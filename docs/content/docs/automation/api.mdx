Everything the console does with your apps and providers is also an HTTP API
under `/v2/admin`. Use it from a script or CI job with a management key. A
coding agent is better served by the [CLI](/automation/cli) or the
[MCP server](/automation/mcp), which keep secrets out of its view.

## Management keys

Open the console's **Access** page and click **New key**. Give the key a name,
choose what it may do, and click **Create key**:

- **Manage**: everything your role allows: create, change and delete apps,
  providers and keys.
- **Read only**: lists and inspects apps, providers and usage, but cannot
  change them.

A dialog titled **Copy your new key now** shows the key once. The gateway keeps
only a hash. Store it in your secret manager. Only an owner or admin can create
one.

A key acts in the account it was created in, with the grant you chose and no
more than its creator's role. The **Access** page lists every key, with its
grant and status, beside your CLI sign-ins and MCP connections. **Revoke key**
stops it at once. The **Access** routes, which list, create and revoke
management keys, CLI sign-ins and MCP connections, need a person signed in to
the console: a management key or token is refused with `403 session_required`.

## Making a call

Send the key as a bearer token:

```sh
curl https://api.appaigateway.com/v2/admin/apps \
  -H "Authorization: Bearer $AGW_MANAGEMENT_KEY"
```

<Callout title="Self-hosting">
  Use your gateway's own address in place of `https://api.appaigateway.com`.
</Callout>

`GET /v2/admin/session` answers who the key is: the account, your role and the
key's grant. Call it first when something is refused.

An OAuth access token from an MCP client or a CLI sign-in works the same way,
with its own grant.

A refusal is `{ "error": { "code": "…", "message": "…" } }`, like the
gateway's other errors. The codes, and what to do about each, are in the agent
manual's [Errors](/automation/agent-manual#errors).

## What you can do

| Area | Routes |
| --- | --- |
| Who is calling | `GET /v2/admin/session` |
| Prices and provider types | `GET /v2/admin/prices`, `GET /v2/admin/provider-types` |
| Provider connections | `GET`, `POST /v2/admin/providers`, `POST /v2/admin/providers/test`, `GET`, `PUT`, `DELETE /v2/admin/providers/{id}` |
| Apps | `GET`, `POST /v2/admin/apps`, `GET`, `PUT`, `PATCH`, `DELETE /v2/admin/apps/{app}` |
| Checking apps | `POST /v2/admin/app-drafts/validate`, `POST /v2/admin/apps/{app}/validate`, `GET /v2/admin/apps/{app}/check`, `GET /v2/admin/apps/{app}/snippet` |
| App keys | `GET`, `POST /v2/admin/apps/{app}/keys`, `POST /v2/admin/apps/{app}/keys/{key}/revoke` |
| End users | `GET /v2/admin/apps/{app}/users`, `GET /v2/admin/apps/{app}/users/{user}`, `POST …/block`, `POST …/unblock` |

## Check before you write

`POST /v2/admin/app-drafts/validate` checks a new app's `{ name, config, status? }`
as a create would, and `POST /v2/admin/apps/{app}/validate` checks a change to
an existing app. Both save nothing, and need only the **Read only** grant. Send
`name`, `config` and `status` only: validation refuses a `revision`. Add the
revision when saving a change to an existing app.

`GET /v2/admin/apps/{app}/check` lists every connection the app's routes and
presets name, with its status. `ready` means the app is active and at least one connection its routes or
presets use can be reached: one that is active, or, for a preset, a first
connection turned off with an active fallback. It checks connection status
only, not that a request will serve. It sends no provider request, so it does not test a key, a device or a
sign-in. Confirm with a real request, or the example requests from
`GET /v2/admin/apps/{app}/snippet`.

## Changing an app

Every app has a `revision`, which each save raises by one. A change sends the
revision it read, and is refused with `409 app_revision_conflict` if someone
saved the app since. Read it again, and make your change on top.

To replace the whole app, send `PUT /v2/admin/apps/{app}` with `name`, `config`,
`status` and `revision`, as `GET` answered them. Leave out `id`, `created_at`,
`updated_at` and `warnings`.

To change a few settings, send `PATCH` with `revision` and `operations`, a JSON
Patch:

```json
{
  "revision": 4,
  "operations": [
    { "op": "replace", "path": "/config/limits/per_app/requests/per_minute", "value": 600 },
    { "op": "replace", "path": "/status", "value": "disabled" }
  ]
}
```

Each operation is `add`, `replace` or `remove`, at a path under `/name`,
`/status` or `/config`. They apply in order, and nothing is saved unless all
of them apply and the result passes the same checks as `PUT`. `null` sets a
limit to unlimited; only `remove` deletes a field.

A provider connection has a `revision` too, for `PUT /v2/admin/providers/{id}`.

Older clients read and write these documents too, so keep settings you do not
know as you read them, and send them back unchanged.

## Example: a server app and its key

```sh
curl https://api.appaigateway.com/v2/admin/apps \
  -H "Authorization: Bearer $AGW_MANAGEMENT_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Backend",
    "config": {
      "authentication": { "type": "api_key", "end_user": { "source": "none" } },
      "routing": { "providers": { "openai": { "operations": ["openai.chat"] } } }
    }
  }'
```

The answer is `201` with `app` and, for a server app, `api_key`: the app's first
key, shown this once. Store `api_key.key` straight in your secret manager.
`POST /v2/admin/apps/{app}/keys` with a `name` makes another one, also shown
once.

A script that may retry, or must never see the key, uses the
[reserved create](/automation/agent-manual#retrying-creation-safely) instead.
