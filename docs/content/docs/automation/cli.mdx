`agw` manages your account from a terminal: provider connections, apps, their
keys, limits and users, and usage. It is made for people and coding agents
alike. Secrets never reach its output: a provider key comes from a hidden
prompt, stdin or the console, and a new app key goes to a private file.

## Install

agw 2 manages this version of the gateway. It needs Node.js 22.19 or later:

```sh
npm install -g @maxceem/agw@2
agw --help
```

<Callout title="Release">
  agw 2 is published as `@maxceem/agw` 2.0 with this version of the gateway.
  agw 1.x manages the earlier version only, and agw 2 manages this one only:
  each stops with a short message at the other.
</Callout>

## Sign in

```sh
agw account login
```

With a browser on this machine, `agw` opens the console, you approve, and the
browser comes back to the terminal. Over SSH, without a display, or with
`--device`, it prints a link and a short code instead: open the link in any
browser, check the code matches, and approve. `--no-open` prints the link
without opening a browser.

The sign-in renews itself while the CLI uses it. It is listed on the console's
**Access** page, where you can revoke it, and `agw account logout` ends it.
Signing in does not create an account: create one in the console first, or on
the sign-in page that opens.

`agw` talks to the hosted service unless you connect it to another gateway:

```sh
agw deployment connect --url https://console.example.com
agw deployment connect --cloud      # back to the hosted service
agw deployment status               # which gateway, and who is signed in
agw account status                  # the account, your role and the grant
```

The URL is the gateway's console address. `deployment connect` signs in too.

### Scripts and CI

Set `AGW_MANAGEMENT_KEY` to a [management key](/automation/api#management-keys)
instead. It is used for every command and overrides the saved sign-in, and
nothing is stored. Pass it from your CI's secret store, never as a command-line
argument.

## Commands

A few commands are built into `agw`, because they need this machine: a
browser, a hidden prompt, a private file or a wait. Every other command comes
from the gateway you are connected to, so a new gateway release brings its
commands without an `agw` update. `agw --help` lists both, once it can reach
the gateway, and `agw <command> --help` lists a command's flags.

A gateway command's flags follow the gateway's argument names: `team_id`
becomes `--team-id`. A value that is a list is given once per value, and a JSON
value is written inline or read from a file with `@path`.

### Providers

```sh
agw provider types                              # every provider and its operations
agw provider add --type openai                  # the key goes in a hidden prompt
agw provider add --type openai --key-stdin < key.txt
agw provider add --type openai --browser        # a person types the key in the console
agw provider list
agw provider show openai
agw provider rotate-key openai                  # a new key, by id or slug
agw provider update <id> --status disabled --revision 3
agw provider remove <id>
```

`provider update` needs the connection's `revision`, from `provider list`.
`provider add` also takes `--name`, `--slug`, `--base-url`, `--pricing` and,
for a custom provider, `--key-header`, `--key-format` and `--path` (once per
path, in the [Listing paths](/providers/custom-base-urls#listing-paths) format).
For Cloudflare AI Gateway, add `--cloudflare-account-id` and
`--cloudflare-gateway-id` with `--browser`: the person approving types the
Cloudflare token in the console. See [Add a provider key](/providers/add-a-provider).

### Apps

```sh
agw app add --type server --name "Backend" --providers openai
agw app add --type ios --name "My App" --team-id ABCDE12345 --bundle-id com.example.app \
  --providers openai=openai.responses+openai.chat
agw app list
agw app show <app>
agw app check <app>            # can it serve requests? sends no provider request
agw app snippet <app>          # example requests for its routes and presets
agw app validate <app> --config @app.json
agw app update <app> --name "New name" --status disabled
agw app replace <app> --config @app.json
agw app remove <app>
```

- `--providers` allows a connection on the new app. A slug alone allows the
  connection's first operation, as the console does; `slug=op+op` names the
  operations.
- `app add --dry-run` checks the app without creating it. `--file` reads the
  whole app document, `{ name, config, status? }`, from a file.
- A server app's first key is written to a private file, never printed. The
  answer names the file. `--key-output <path>` chooses it; an existing file is
  never overwritten.
- `app update --operations` applies a JSON Patch to the app, with `--revision`
  from `app show`. See [Changing an app](/automation/api#changing-an-app).
- `app replace` saves a whole document, with the `revision` inside it.
  `app validate` takes the same document without `revision`, which it refuses.
- `app snippet` gives a preset with fixed parameters only a note with its URL,
  by design: what its request becomes cannot be shown safely.

### Keys, users and usage

```sh
agw app key add <app> --name ci      # written to a private file
agw app key list <app>
agw app key revoke <app> <key>
agw app user list <app>
agw app user block <app> <user>
agw usage show                       # this month, every app
agw usage show --app <app>
agw usage breakdown --app <app> --by model
agw app charge list <app>
agw app auth-event summary <app>
agw app conversations <app> --from 2026-11-01 --media
```

`app conversations` downloads an app's [stored conversations](/applications/conversations)
into a folder, `--output`, with their media when you add `--media`.

### Browser steps

`provider add --browser` and `provider rotate-key --browser` open a console page
where a person types the key and approves, within 15 minutes. The page's link
carries its own proof, so `agw` never prints it: it opens it in a browser on
this machine, or, with `--no-open` or no browser, saves it in a file only you
can read and says where.

`agw` then waits for the person. With `--json` or `--no-input` it answers at
once with `state: "pending"` instead. So a browser step suits a person at this
machine; from another machine, add the key on the console's **Providers** page. A pending result has not finished: run
`agw operation wait <id>` to wait. A wait that times out does not cancel the
step; run `operation wait` again.

### Removals

A command that cannot be undone, such as `app remove`, asks you to type `yes` on
a terminal. With `--json`, or without a terminal, it needs `--yes` instead,
which an agent adds only after the person it works for agreed.

## Output

- `--json` prints one JSON document: `{ "schemaVersion": 1, "ok": true, "result": … }`,
  or `"ok": false` with `error.code`, `error.message` and `error.nextAction`.
  Its fields only grow from one release to the next. `--help` prints text.
- `--no-input` never prompts. A command that would have to ask fails instead.
- Text output and errors go to stdout and stderr, so a redirected stdout never
  holds half an error.

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Done. A browser step may still be pending: check `state` |
| `2` | The command line is wrong |
| `3` | The gateway or the network failed |
| `4` | A state or a decision stops it, such as a missing confirmation |
| `5` | `agw` stopped waiting. A browser step is still open; a browser sign-in must start again |

After some refusals, when the gateway's release differs from `agw`'s, the
output adds a notice saying which side to update.

## Where agw keeps things

The sign-in, and pending browser steps, are in a private folder:
`~/.local/state/agw/v2` (or `$XDG_STATE_HOME/agw/v2`), and
`%LOCALAPPDATA%\agw\v2` on Windows. App keys `agw` writes without
`--key-output` go to its `app-keys` folder. Keep the folder after an
interrupted command, so `agw` can pick up what was pending.

## Compatibility

An installed `agw` keeps working as the gateway gets newer:

- answers and app settings only gain fields, and `agw` keeps and sends back
  settings it does not know;
- a command edits only what its flags name;
- the gateway's commands arrive with the gateway. When one changed since `agw`
  read it, `agw` reads the list again and may retry, or refuses with
  `tool_changed` rather than run it blind. A command that needs a newer `agw`
  is refused with `cli_outdated`.

## Human support

`agw support send --type support --message-stdin < note.txt` emails support for
the signed-in person (`--type` is `bug`, `support` or `feedback`), who gets the reply by email. Without a terminal it needs
`--yes`: show the person the message first. Never put a key or token in it.
