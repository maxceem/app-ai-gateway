title: MCP server
description: Connect an MCP client such as a coding agent to your gateway, and let it read and change your apps, providers and usage.
---

The gateway is also a [Model Context Protocol](https://modelcontextprotocol.io)
server. An MCP client, such as a coding agent, a desktop assistant or an IDE,
can connect to it to read your apps, providers and usage, and to change them.
Each tool runs the same operation the [API](/automation/api) and the
[CLI](/automation/cli) run, with the same rules. No key or token ever passes
through a tool, in either direction.

## Connect

Add this address to your client's remote MCP servers:

```text
https://console.appaigateway.com/v2/mcp
```

Most clients then sign in on their own: your browser opens the console, and you
approve the connection. Then ask the agent to call `get_account` and read
`agw://guide` before it changes anything. For example: "Check my app's
settings and show its example requests; do not send any AI request." It can do
that with `check_app` and `get_app_snippet`.

<Callout title="Self-hosting">
  Use your console's address followed by `/v2/mcp`. The endpoint answers only
  on the console's address, never on a separate API host.
</Callout>

## Connect with OAuth

Give the client the address and nothing else.

1. The client's first request is refused with `401` and a challenge naming
   `/.well-known/oauth-protected-resource/v2/mcp` on the console. From there it
   finds the console's sign-in.
2. The client opens your browser at a page titled **Connect an app to your
   account**. It shows the client's name, as the client states it, beside the
   domain that vouches for it, and what it **Asks for**.
3. You choose:
   - **Signed in:** which of your accounts the client may use, and what it may
     do, then **Allow**. **Manage** is everything your role allows. **Read only**
     lists and inspects, and every change tool refuses it with
     `grant_insufficient`.
   - **Not signed in:** **Sign in**, or **Create an account**, and you come
     back to the same page.
   - **Deny** sends the client away with nothing.
4. The browser returns to the client, which receives its tokens and renews
   them on its own.

The page stays valid for ten minutes.

| What | How long |
| --- | --- |
| Access token (`agw_oat_…`) | 10 minutes |
| Refresh token (`agw_ort_…`), and so the connection | 30 days, starting again at each renewal |

So a client used at least once a month stays connected until you revoke it. The
console's **Access** page lists each connection with its client, grant and
account. **Revoke connection** ends it, and the client must be approved again.

## Connect with a management key

Create a [management key](/automation/api#management-keys) on the **Access**
page, with the **Read only** or **Manage** grant, and give it to the client as
an `Authorization: Bearer` header. Keep it out of the client's settings file
where you can. A client that reads environment variables, such as Claude Code
with a project `.mcp.json`, can take it from there:

```json title=".mcp.json"
{
  "mcpServers": {
    "app-ai-gateway": {
      "type": "http",
      "url": "https://console.appaigateway.com/v2/mcp",
      "headers": { "Authorization": "Bearer ${AGW_MANAGEMENT_KEY}" }
    }
  }
}
```

The server reads only the `Authorization` header, never a console sign-in
cookie. Revoking the key on the **Access** page ends the client's access.

## Reading tools

These change nothing and never send a request to a provider.

| Tool | What it answers |
| --- | --- |
| `get_account` | Who you are, the account, your role and the grant. Call it first |
| `list_models` | The priced models |
| `list_provider_types` | Every provider type and its operations |
| `list_providers`, `get_provider` | Your provider connections, as metadata; never a key |
| `list_apps`, `get_app` | Your apps, and one app's whole document with its revision |
| `validate_app` | Whether an app document would be accepted, without saving it |
| `check_app` | Each connection the app names, with its status, and `ready`: a connection-status check that sends no request and does not prove one will serve |
| `get_app_snippet` | Example requests for the app, with no credential in them |
| `list_app_keys` | A server app's keys, as metadata |
| `list_app_users`, `list_app_seen_users`, `get_app_user` | An app's end users, the user ids only its usage names, and one user with its usage |
| `get_usage` | One month's totals, for one app or all of them |
| `get_usage_breakdown`, `get_usage_timeseries` | An app's usage by one dimension, or by day |
| `list_app_charges` | An app's charges, one by one |
| `list_app_jobs` | An app's jobs, and the estimates not yet settled |
| `get_auth_event_summary`, `list_auth_events`, `list_rejection_events` | Why an app's users cannot sign in or are refused |
| `get_operation` | Where a creating tool's step stands |

## Change tools

| Tool | What it does |
| --- | --- |
| `add_provider`, `rotate_provider_key` | Answer a console page where a person enters the provider's key |
| `update_provider` | Rename a connection, change its prices, or turn it off |
| `remove_provider` | Delete a connection for good |
| `add_app`, `add_app_key` | Create an app or a server app key, in two calls |
| `patch_app` | Change some of an app's settings |
| `update_app` | Replace an app's whole document |
| `remove_app` | Delete an app for good |
| `revoke_app_key` | Revoke a server app's key |
| `block_app_user`, `unblock_app_user` | Block or unblock one of an app's users |
| `contact_support` | Email human support for you, where the gateway offers it |

`patch_app`, `update_app` and `update_provider` take the `revision` the agent
read: a change someone made since is refused, never overwritten. The removals
take the ID twice, as the ID and as `confirm`. Prefer turning an app or a
connection off, which can be undone.

### A key is entered in your browser

`add_provider` takes `{ type, name, slug?, baseUrl?, pricing?, cloudflareGateway?: { accountId, gatewayId } }`;
other top-level fields are refused. `rotate_provider_key` takes `{ id, revision }`.
Each answers a console page for you to open and enter the key. When adding a
connection through Cloudflare, you enter the Cloudflare token (required) and the
provider key (optional). A rotation takes the new provider key only, never a
Cloudflare token. The
agent polls `get_operation` until `completed` or `expired`. A custom provider,
listed paths and Vercel's pinned serving providers are set in the console. See
[Providers](/automation/agent-manual#providers) in the agent manual.

### Creating takes two calls

`add_app` takes `{ config: { name, config, status? }, handle? }` and
`add_app_key` takes `{ app, name, handle? }`. The first call reserves, the
second, with the answer's `handle`, creates once. A new key is never in the
answer: open `reveal_url`, signed in as an owner or admin, and click
**Reveal the key**. See
[Retrying creation safely](/automation/agent-manual#retrying-creation-safely).

### What a tool never shows

A field named like a credential, such as `secret`, `token`, `api_key` or
`password`, is refused in a tool's arguments, and shown as `[redacted]` in its
answers. Names such as `secretHint` or `max_tokens` are not credentials. If
`get_app` shows `[redacted]` inside an app's settings, the agent must not send
that marker back: have the person make that change in the console or the CLI.

## Answers and refusals

Each answer has a short summary for the agent and the same body the API answers
with. A refusal from a tool is an answer marked as an error, with the gateway's
error code, its message, and what to do next. The endpoint itself answers HTTP
errors instead: `401` for a missing or invalid credential, `403` for a browser
origin it does not serve, and `405` for `GET` or `DELETE`.

`agw://guide` is a resource with the full rules for working with the gateway
over MCP. It is written into the server itself, so an agent connected to any
deployment can read it.

## Calling from a browser

Most MCP clients are not browsers and send no `Origin` header, so the origin
check does not apply to them; they still need a valid credential. A request
from a web page is served only from the console's own address, or from an
address the deployment lists; every other one is refused with `403`.

## For MCP client developers

The server speaks the Streamable HTTP transport over `POST`, with no session to
keep: every request carries its credential. Clients on the `2026-07-28`
protocol revision and on the 2025 revisions are both served.

A client usually names itself with an `https` address as its `client_id`: a
small JSON document describing it, which the gateway reads. Only the return
addresses it lists can receive the result. A deployment can also register
clients itself, and can turn these documents off. There is no client secret and
no dynamic client registration.

The OAuth addresses, all on the console:

| Address | What it is |
| --- | --- |
| `/.well-known/oauth-protected-resource/v2/mcp` | What the MCP endpoint points to |
| `/.well-known/oauth-authorization-server/v2` | The sign-in server's details |
| `/v2/oauth/authorize` | The browser step, with PKCE (`S256`) |
| `/v2/oauth/token` | Code exchange and renewal |
| `/v2/oauth/revoke` | A client ending its own connection |

The scopes are `read` and `manage`.
