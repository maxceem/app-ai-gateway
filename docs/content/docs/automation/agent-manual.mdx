Manage App AI Gateway on a person's behalf with the CLI (`agw`), the MCP server
or the management API. This manual is also served as plain markdown at
[https://docs.appaigateway.com/agents.md](https://docs.appaigateway.com/agents.md).
Use [the documentation index](/llms.txt) to find the guide for a task. When the
gateway and these pages disagree, trust the gateway: `agw <command> --help`, the
MCP tool list and `agw://guide` come from the gateway you are connected to.

## Choose the connection before changing anything

Hosted addresses:

| Purpose | Address |
| --- | --- |
| Console, sign-in, browser steps and the CLI | `https://console.appaigateway.com` |
| MCP | `https://console.appaigateway.com/v2/mcp` |
| App requests and the management API | `https://api.appaigateway.com` |

A self-hosted gateway has its own console address, and may answer the API on
the same address. Do not deploy anything unless the person asked for that. Use
the links the gateway answers for browser steps; never build them yourself.

With MCP, call `get_account` first and read `agw://guide`; see "MCP" below.
With the CLI, check where it is connected first:

```sh
agw deployment status --json --no-input
agw account status --json --no-input
```

- **Not signed in:** run `agw account login --no-open --json --no-input`. Give
  the person the link and the code. They open it in their own browser, check the
  code, and approve. Signing in never creates an account: the person needs one
  already, made in the console.
- **Another gateway:** `agw deployment connect --url <console address>` connects
  and signs in. `agw deployment connect --cloud` goes back to the hosted service.
- **A management key from the person:** use it as the `AGW_MANAGEMENT_KEY`
  environment variable, from their secret store. It overrides the saved sign-in
  and is never saved. Never put it in a command argument.

A saved sign-in is not proof of the right account: compare the account
`account status` names with the one the person means.

## CLI task workflow

1. Read `agw provider list --json` and `agw app list --json`. Reuse the IDs and
   slugs they answer. Look at an app with `agw app show <app> --json`.
2. For a missing provider, tell the person which one, and ask them to add its
   key themselves: on the console's **Providers** page, or with
   `agw provider add --type <type>` on their own machine, which asks for the key
   in a hidden prompt. Then check `agw provider list` and carry on. Never ask
   for a key in the chat, and never read or pass on a browser step's link file.
3. Read the command's `--help`, then make the change. For an iOS app, use the
   person's Team ID and Bundle ID. For a server app, keep its key in the private
   file `agw` names, or a new path given with `--key-output`.
4. To allow a provider on a new app, use `--providers <slug>` (its first
   operation) or `--providers <slug>=<op>+<op>`. `agw provider types` lists each
   provider's operations.
5. To change an existing app:
   - `agw app update <app> --name … --status …` changes only those.
   - For any other setting, `agw app update <app> --operations @patch.json
     --revision <n>`, with the revision from `app show`. The file is a JSON
     Patch: `add`, `replace` or `remove` at paths such as
     `/config/limits/per_app/requests/per_minute`.
   - `agw app replace <app> --config @app.json` saves a whole document:
     `name`, `config`, `status` and `revision` from `app show`, and every
     setting you found there, including ones you do not recognize.
   - Check first with `agw app validate <app> --config @app.json --json`.
   - A stale revision is refused with `app_revision_conflict`: read the app
     again, apply the change on top, and repeat.
6. Run `agw app check <app> --json` and `agw app snippet <app> --json`. The
   check reads settings only: it tests no provider key, device, sign-in or
   subscription. Do not send AI requests unless the person asked.
7. Report as described in "Reporting back". A pending browser step is pending,
   never done.

Commands not built into `agw` come from the gateway: `agw --help` lists them.
For every command, use `--json --no-input`, and add `--no-open` for a browser
step. `--json` answers `{schemaVersion: 1, ok: true, context, result}` or
`{schemaVersion: 1, ok: false, error}`, either with optional `notices`. Follow
`error.nextAction`.

- A removal runs only with `--yes`, once the person has agreed.
- Exit codes: `0` done, `2` wrong command line, `3` gateway or network failure,
  `4` a state or decision stops it, `5` stopped waiting while the step is still
  open. A wait that times out cancels nothing: `agw operation wait <id>` again.
- A `newer_gateway` notice means the gateway has settings this `agw` does not
  know. They are kept when it saves; tell the person to update `agw` before
  changing them. A `version_mismatch` notice after a failure names which side
  to update.

## MCP

The MCP server's tools run the same operations as the CLI and the API. A client
connects with OAuth on its own: the person approves it in their browser,
choosing the account and **Read only** or **Manage**. A management key as a
bearer token works too.

- Start with `get_account`. It names the account, the person, their role and
  the grant. A **Read only** grant refuses every change with
  `grant_insufficient`.
- Read before you write: `list_providers`, `list_apps`, `get_app`.
- For a small change, use `patch_app` with the revision `get_app` answered. It
  changes only the paths you name. `update_app` replaces the whole document.
- A provider key is never a tool argument. `add_provider` and
  `rotate_provider_key` answer a link where the person types the key; then poll
  `get_operation` with the answer's `id` until it completes. Never open the
  link yourself.
- `add_app` and `add_app_key` take two calls: see "Retrying creation safely".
  A new key is never in a tool answer: give the person `reveal_url`.
- A field shown as `[redacted]` holds a secret. Never send that marker back.
  Have the person change that setting in the console or the CLI.
- A refusal is a tool answer marked as an error, with the gateway's code and the
  next step.

The full rules are in the server's `agw://guide` resource.

## The management API

For an integration without the CLI or MCP:

- Base address: `https://api.appaigateway.com`, or the self-hosted gateway's
  own. Every route is under `/v2/admin/`, with JSON bodies.
- Send the management key as `Authorization: Bearer agw_mgmt_…`. A key has its
  grant, `read` or `manage`, and no more than its owner's role. It never
  expires on its own.
- `GET /v2/admin/session` answers the account, role and grant. Call it first.
- Keys, CLI sign-ins and MCP connections are managed only in the console:
  their routes answer a key with `403 session_required`.

See [Use the API](/automation/api) for the routes.

## What the gateway is

App AI Gateway sits between a person's apps and AI providers such as OpenAI,
Anthropic and Gemini. The person adds each provider key once, as a **provider
connection** with a slug. Each **app** has a permanent ID and its own settings:
how it signs in, which connections, operations and models it may use, presets,
limits on its users, and whether its conversations are kept. Apps call:

- `{API}/v2/apps/{app}/proxy/{slug}/{provider_path}`, with the provider's own
  request format;
- `{API}/v2/apps/{app}/presets/{name}`, for a preset.

See [Apps and providers](/how-it-works/apps-and-providers).

## Rules

1. Never print, log or repeat a secret: a management key, a provider key, an
   app key or a token. When a key is created, keep it in a private file, or let
   the person see it on its reveal page, and report only where it is.
2. Never send `id` when creating an app. The gateway makes the ID from the name
   and answers it as `app.id`. It never changes.
3. Validate an app before saving it: `POST /v2/admin/app-drafts/validate` for a
   new one, `POST /v2/admin/apps/{app}/validate` for a change.
4. Read before you write. List providers and apps first, so you use slugs and
   IDs that exist.
5. A change to an app sends the `revision` you read. `PUT` replaces the whole
   app: send back `name`, `config` and `status` as read, with your change, and
   leave out `id`, `created_at`, `updated_at` and `warnings`.
6. Keep settings you do not recognize exactly as you read them.
7. Prefer what can be undone. Turn an app or a connection off rather than
   deleting it, unless the person asked for the deletion.
8. Saved changes usually reach live requests within a minute, and a block
   within ten seconds. See [When changes take effect](/how-it-works/apps-and-providers#when-changes-take-effect).
9. Do not send AI requests to test a setup unless asked: each one costs the
   person money.
10. An app's `warnings` name behaviour that will stop on a date. Tell the
    person about each one.

## Errors

Every refusal is `{ "error": { "code": "…", "message": "…", "data": { … } } }`.

| Status | Code | What to do |
| --- | --- | --- |
| 400 | `invalid_request` | Fix what `message` names |
| 400 | `pricing_not_configured` | A model has no price. Use a priced model, or have the person add a price |
| 400 | `app_revision_required` | Send the revision from your read |
| 401 | `auth_required` | The credential is missing, wrong or revoked |
| 403 | `grant_insufficient` | Ask the person for a **Manage** grant |
| 403 | `forbidden` | The person's role does not allow it |
| 403 | `session_required` | Only the person, in the console, can do this |
| 404 | `not_found`, `app_not_found`, `provider_not_found`, `key_not_found` | Nothing with this ID in the account |
| 409 | `conflict`, `app_revision_conflict` | Read it again and apply the change on top. On a provider create, the slug is taken: choose another |

The errors apps get on their requests are in [Errors and limits](/integrate/errors).

## Workflow for setting up an app

1. `GET /v2/admin/providers`. Note each connection's `type` and `slug`.
2. If one is missing, ask the person to add its key themselves, on the
   console's **Providers** page or with `agw` on their own machine. Over MCP,
   `add_provider` answers a console link to give them.
3. Compose the app from the reference below.
4. `POST /v2/admin/app-drafts/validate` with it. Fix every refusal.
5. Create it through a reserved create ("Retrying creation safely"), or
   `POST /v2/admin/apps` where a lost answer is not a risk. A server app's first
   key is in the plain create's answer once, or on the reserved create's reveal
   page.
6. `GET /v2/admin/apps/{app}/check` and `GET /v2/admin/apps/{app}/snippet`.
7. Report back.

## Providers

| Call | Body | Notes |
| --- | --- | --- |
| `GET /v2/admin/provider-types` | | Each type, its operations, and whether it can go through Cloudflare |
| `GET /v2/admin/providers` | | `providers[]`: `id`, `type`, `slug`, `name`, `status`, `secretHint`, `baseUrl`, `cloudflareGateway`, `passthrough`, `pricing`, `revision` |
| `POST /v2/admin/provider-handoffs` | Everything the create takes but `secret` | Answers a link where the person types the key. Use this, not a plain create |
| `POST /v2/admin/providers/test` | `type`, `secret`, `baseUrl`, `cloudflareGateway`, `auth` | Tries a key without saving. Only `reason: "rejected"` says the key is probably wrong |
| `PUT /v2/admin/providers/{id}` | `revision` and any of `name`, `pricing`, `status`, `passthrough`, `baseUrl`, `cloudflareGateway`, `servingProviders` | `status: "disabled"` pauses it and keeps the key and slug |
| `POST /v2/admin/providers/{id}/key-handoffs` | `revision` | A link where the person types a new key |
| `DELETE /v2/admin/providers/{id}` | | For good, with its prices. Apps that use it start failing |

The first connection of a type usually takes the type as its slug, such as
`openai`. Another one of the same type needs its own slug.

A model needs a price, from the price list (`GET /v2/admin/prices`) or the
connection's own `pricing`, unless the provider reports each request's cost.
See [Model pricing](/providers/model-pricing). Base URLs, custom providers and
listed paths are in [Custom base URLs](/providers/custom-base-urls), and
Cloudflare and Vercel AI Gateway in [their guide](/providers/gateways).

## Applications

| Call | Body | Notes |
| --- | --- | --- |
| `GET /v2/admin/apps` | | `apps[]` |
| `GET /v2/admin/apps/{app}` | | `{ app: { id, name, config, status, revision, created_at, updated_at, warnings? } }` |
| `POST /v2/admin/app-drafts/validate` | `{ name, config, status? }` | Judged as a create. Saves nothing |
| `POST /v2/admin/apps/{app}/validate` | `{ name, config, status? }` | Judged as a change of that app. Saves nothing |
| `POST /v2/admin/apps` | `{ name, config, status? }` | Answers `app`, and for a server app `api_key` once |
| `PUT /v2/admin/apps/{app}` | `{ name, config, status?, revision }` | Replaces the whole app |
| `PATCH /v2/admin/apps/{app}` | `{ revision, operations }` | JSON Patch `add`, `replace` or `remove` under `/name`, `/status` or `/config` |
| `GET /v2/admin/apps/{app}/check` | | `ready`, and each connection the app names with its status |
| `GET /v2/admin/apps/{app}/snippet` | | Example requests for every route and preset, with no credential in them |
| `DELETE /v2/admin/apps/{app}?confirm={app}` | | For good: its keys, users and App Attest keys go; its usage history stays |
| `GET /v2/admin/apps/{app}/keys` | | Server apps only |
| `POST /v2/admin/apps/{app}/keys` | `{ name }` | Answers the key once |
| `POST /v2/admin/apps/{app}/keys/{key}/revoke` | | |

`status` is `active` or `disabled`. A disabled app refuses every request with
`403 app_disabled`, and keeps everything.

## Application configuration reference

`config` is one JSON object with five parts. Unknown keys are refused when you
save. Each part's guide explains its choices; this is the shape.

```json
{
  "authentication": { … },
  "routing": { … },
  "limits": { … },
  "presets": { … },
  "conversations": { … }
}
```

Only `authentication` is required. A field left out takes its default.

### `authentication`

An iOS app, `type: "apple_app_attest"`:

| Key | Meaning |
| --- | --- |
| `app_attest.team_id` | The Apple Team ID: ten uppercase letters or digits |
| `app_attest.bundle_id` | The bundle ID |
| `app_attest.environments` | `["production"]` (the default), `["development"]`, or both |
| `app_attest.verify_on` | `every_request` (the default): every request carries `X-AppAttest-Proof`. `token_exchange`: only getting a token is checked |
| `end_user` | `{ "source": "app_install" }` to count each install as a user, or `{ "source": "issuer", "issuer": { … } }` for signed-in users |

A server app, `type: "api_key"`:

| Key | Meaning |
| --- | --- |
| `end_user` | Required. `{ "source": "none" }` for no users; `{ "source": "header", "header": "x-end-user-id" }` when the server names the user; `{ "source": "issuer", "issuer": { … } }` for signed-in users |

The `issuer` object:

| Key | Meaning |
| --- | --- |
| `jwks_url` | Where the identity provider publishes its keys. `https` only |
| `issuer`, `audience` | Accepted `iss` and `aud` values: a string, or a list |
| `user_id_claim` | The claim used as the user ID, usually `"sub"` |
| `required_claims` | Claims a paid user must have: each `{ "path", "contains" }` or `{ "path", "equals" }`. `[]` for none |
| `max_token_lifetime_seconds` | Refuse a token whose own lifetime is longer, such as `86400` |
| `token_header` | Optional. One more header that may carry the gateway token |
| `provider` | Optional: `firebase`, `supabase`, `auth0`, `clerk` or `custom`, so the console shows the same choice |
| `entitlement` | Optional: `revenuecat` or `custom`, for the same reason |

The settings for each identity provider are in
[User authentication](/applications/auth-policy/user-authentication). A
RevenueCat check is `{ "path": "revenueCatEntitlements", "contains": "<entitlement>" }`;
see [Subscription check](/applications/auth-policy/subscription-check).

### `routing`

| Key | Meaning |
| --- | --- |
| `providers` | Keyed by connection slug. A slug not listed is not allowed |
| `providers.<slug>.operations` | Operations the app may use on that connection, such as `["openai.responses"]`. At least one. `passthrough` allows its listed paths |
| `providers.<slug>.models` | Optional. Allowed models. Left out, every priced model |
| `providers.<slug>.max_output_tokens` | Optional. The most output tokens a request may ask for |
| `model_rewrites` | Optional. A model name the app sends, mapped to the model sent. The target needs a price |

See [Provider access](/applications/provider-access) and
[Model rewrites](/applications/model-rewrites).

### `limits`

Two parts, `per_user` and `per_app`, each with the same fields. `null` means no
limit, and is the default.

| Key | Meaning |
| --- | --- |
| `requests.per_minute`, `requests.per_day` | Request limits. Positive whole numbers |
| `spending.monthly_nano` | A monthly budget in nano-dollars: `1000000000` is $1. `0` stops all spend |
| `per_user.spending.scope` | Whose month a per-user budget counts: `apple_account` (iOS default), `install`, or `user` (server default, and on iOS only with signed-in users) |

`per_user` limits need an app that names its users. On an iOS app, per-user
request limits count per install. See [Limits and blocking](/how-it-works/limits)
and [Limits](/applications/limits).

### `presets`

Keyed by name: 1 to 64 characters from `a-z`, `0-9` and `-`.

| Key | Meaning |
| --- | --- |
| `provider` | A connection slug |
| `operation` | The operation it sends, such as `openai.responses` |
| `model` | The model. Needs a price, unless the provider reports its cost |
| `params` | Optional. Merged into each JSON request, winning over the app's values |
| `max_output_tokens` | Optional |
| `fallback` | Optional. A list of `{ provider, model, operation? }` tried in order after no answer, a `429` or a `5xx`. Each speaks the same format |

See [Presets](/applications/custom-endpoints).

### `conversations`

Optional, and off unless `store` is `true`.

| Key | Meaning |
| --- | --- |
| `store` | Keep a copy of every call the app makes, and its answer |
| `keep.images`, `keep.audio`, `keep.files` | Which attachments are kept beside it. Each defaults to `true` |
| `retention_days` | Days to keep them, 1 to 400. Default `180` |

Turn it on only when the person asks, and remind them to say so in their privacy
policy. See [Conversation history](/applications/conversations).

### Examples

A server app whose backend names its users, with one OpenAI model:

```json
{
  "name": "Search service",
  "config": {
    "authentication": { "type": "api_key", "end_user": { "source": "header", "header": "x-end-user-id" } },
    "routing": {
      "providers": {
        "openai": { "operations": ["openai.responses"], "models": ["gpt-5.4-mini"], "max_output_tokens": 4096 }
      }
    },
    "limits": {
      "per_user": { "requests": { "per_minute": 30, "per_day": 1000 }, "spending": { "monthly_nano": 10000000000 } },
      "per_app": { "spending": { "monthly_nano": 100000000000 } }
    }
  }
}
```

An iOS app with Firebase sign-in, a RevenueCat check and a preset:

```json
{
  "name": "Calorie Tracker",
  "config": {
    "authentication": {
      "type": "apple_app_attest",
      "app_attest": { "team_id": "ABCDE12345", "bundle_id": "com.example.calorietracker" },
      "end_user": {
        "source": "issuer",
        "issuer": {
          "jwks_url": "https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com",
          "issuer": "https://securetoken.google.com/calorie-1a2b3",
          "audience": "calorie-1a2b3",
          "user_id_claim": "sub",
          "required_claims": [{ "path": "revenueCatEntitlements", "contains": "pro" }],
          "max_token_lifetime_seconds": 86400,
          "provider": "firebase",
          "entitlement": "revenuecat"
        }
      }
    },
    "limits": {
      "per_user": { "requests": { "per_minute": 20, "per_day": 500 }, "spending": { "monthly_nano": 5000000000 } }
    },
    "presets": {
      "chat": {
        "provider": "openai",
        "operation": "openai.responses",
        "model": "gpt-5.4-mini",
        "params": { "reasoning": { "effort": "low" } },
        "fallback": [{ "provider": "xai", "model": "grok-4.5" }]
      }
    }
  }
}
```

## Users and usage

- Users: `GET /v2/admin/apps/{app}/users` (`month`, `status`, `query`, `limit`,
  `offset`), `GET …/users/{user}`, `POST …/users/{user}/block` and
  `…/unblock`. Users an app's server names in a header cannot be blocked here.
  See [Users](/applications/users).
- Usage: `GET /v2/admin/usage` for the month across apps, and under
  `/v2/admin/apps/{app}`: `usage`, `usage/timeseries`, `usage/breakdown`,
  `charges` and `jobs`. See [Usage and charges](/applications/usage#through-the-api).
- Sign-in health: `auth-events/summary`, `auth-events` and `rejection-events`
  under the app. See [Auth events](/applications/auth-events).

## What clients send

You rarely call these, but you may write the code that does:

- A server app with no users: `Authorization: Bearer <app key>` on every
  request.
- A server app with signed-in users: `POST /v2/apps/{app}/auth/token` with
  `{ "api_key", "issuer_token" }`, then `Authorization: Bearer <access_token>`
  and `X-App-Version` on every request.
- An iOS app: App Attest sign-in, then the gateway token, `X-App-Version` and,
  where `verify_on` is `every_request`, `X-AppAttest-Proof`. The Swift package
  for this comes with the v2 SDK; until then, see [iOS apps](/integrate/ios).

See [Server applications](/integrate/server) and
[Calling the provider proxy](/integrate/proxy).

## Contacting human support

Where the gateway offers human support, you can write to it for the person:
`agw support send`, `contact_support` over MCP, or `POST /v2/admin/support`.
Support replies to the person's email address, never to you.

1. Only when the person asked. Show them the exact message first, and send it
   once they agree. Without a terminal, `agw support send` needs `--yes`.
2. Choose the type: `bug`, `support` for a question, or `feedback`.
3. Say what happened, what they expected and what was tried, with IDs and
   codes in `--context key=value`.
4. Never include a key, token or password: a message that looks like it holds
   one is refused, and nothing is sent.
5. Tell the person the answer's `reference`. The same message sent again within
   ten minutes sends nothing new.

```sh
agw support send --type bug --message "Streaming from my-app stops after about 30 seconds since Monday." \
  --context app_id=my-app --yes --json --no-input
```

## Reporting back

When you finish, report what you created or changed, by ID and slug; the URLs
the app calls; where each key was stored, or which reveal page the person must
open; and what you could not do. Never include a secret.

## Retrying creation safely

A plain create is not safe to repeat: if its answer is lost, you cannot tell
whether it happened. For apps and app keys, use a reserved create:

1. `POST /v2/admin/reserved/apps` with `{ name, config, status? }`, or
   `POST /v2/admin/reserved/apps/{app}/keys` with `{ name }`. Nothing is
   created. The answer has `state: "reserved"`, a `handle`, the operation's `id`
   and when it lapses, 15 minutes later.
2. Send the same body again with `handle`. It is created once, and the answer
   has `state: "created"`. Sending it again repeats that answer with
   `replayed: true`.

A server app's key is never in these answers: give the person `reveal_url`,
where an owner or admin sees it once, within 15 minutes. `GET
/v2/admin/operations/{id}` says where an operation stands: `pending`,
`completed` with what it created, or `expired`.

Refusals: `operation_mismatch` when the handle was reserved for other
arguments, `operation_expired` when it lapsed, and `operation_not_found` for a
handle this gateway never gave out.

A provider connection is added by the person, with its key, so it needs no
reserved create. Over MCP or the API, `POST /v2/admin/provider-handoffs` opens
that step for them, and the same operation route says when it is done.
