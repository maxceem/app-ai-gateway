Manage App AI Gateway on a person's behalf with the CLI (`agw`), the MCP server
or the management API. This manual is also served as plain markdown at
[https://docs.appaigateway.com/agents.md](https://docs.appaigateway.com/agents.md).
Use [the documentation index](/llms.txt) to find the guide for a task. When the
gateway and these pages disagree, trust the gateway: `agw <command> --help`, the
MCP tool list and `agw://guide` come from the gateway you are connected to.

## What the gateway is

App AI Gateway sits between a person's apps and AI providers such as OpenAI,
Anthropic and Gemini. The person adds each provider key once, as a **provider
connection** with a slug. Each **app** has a permanent ID and its own settings:
how it signs in, which connections, provider operations and models it may use,
presets, limits on its users, and whether its conversations are kept. With
`{API}` as the API address from the table below, apps call:

- `{API}/v2/apps/{app}/proxy/{slug}/{provider_path}`, with the provider's own
  request format;
- `{API}/v2/apps/{app}/presets/{name}`, for a preset.

See [Apps and providers](/how-it-works/apps-and-providers).

"Operation" names three different things here:

- a **provider operation** is one kind of request a provider serves, such as
  `openai.responses`, which an app allows;
- a **pending step** is a browser step or a reserved create, which
  `agw operation wait` and `get_operation` follow;
- a **patch operation** is one `add`, `replace` or `remove` in a JSON Patch.

## Choose the connection before changing anything

Hosted addresses:

| Purpose | Address |
| --- | --- |
| Console, sign-in, browser steps and the CLI | `https://console.appaigateway.com` |
| MCP | `https://console.appaigateway.com/v2/mcp` |
| App requests and the management API (`{API}`) | `https://api.appaigateway.com` |

A self-hosted gateway has its own console address, and may answer the API on
the same address. Do not deploy anything unless the person asked for that. Use
the links the gateway answers for browser steps; never build them yourself.

With MCP, call `get_account` first and read `agw://guide`; see "MCP" below.
With the CLI, check where it is connected first:

```sh
agw deployment status --json --no-input
agw account status --json --no-input
```

- **Not signed in:** run `agw account login --no-open --json --no-input` as a
  background process, or in a session that shows its output as it runs. It
  waits up to ten minutes for the approval, so a tool that returns only when
  the command ends would keep you from reading the code in time. Send stderr to
  a file only when your background runner needs one. `--no-open` makes it show
  a link and a short code even on a machine with a browser. Both arrive on
  stderr while it waits; the JSON comes on stdout only after approval or
  failure. Read the link and the code as soon as they appear, and give them to
  the person. They open the link in their own browser, check the code, and
  approve. Signing in never creates an account: the person needs one already,
  made in the console.
- **Another gateway:** `agw deployment connect --url <console address>` connects
  and signs in. `agw deployment connect --cloud` goes back to the hosted service.
- **A management key from the person:** use it as the `AGW_MANAGEMENT_KEY`
  environment variable, from their secret store. It overrides the saved sign-in
  and is never saved. Never put it in a command argument.

A saved sign-in is not proof of the right account: compare the account
`account status` names with the one the person means.

## Rules

These apply however you connect: CLI, MCP or API.

1. Never print, log or repeat a secret: a management key, a provider key, an
   app key or a token. When a key is created, keep it in a private file, or let
   the person see it on its reveal page, and report only where it is.
2. Never send `id` when creating an app. The gateway makes the ID from the name
   and answers it as `app.id`. It never changes.
3. Check an app before saving it: `agw app add … --dry-run` or
   `agw app validate`, `validate_app` over MCP, or
   `POST /v2/admin/app-drafts/validate` and `POST /v2/admin/apps/{app}/validate`.
4. Read before you write. List providers and apps first, so you use slugs and
   IDs that exist.
5. A change to an app sends the `revision` you read: `agw app update
   --revision`, `app replace`, `patch_app`, `update_app`, `PATCH` or `PUT`. A
   whole document is `name`, `config` and `status` as read, with your change.
   Leave out `id`, `created_at`, `updated_at` and `warnings`.
6. A setting name the gateway does not know is refused. A setting the gateway
   returned that you do not know must be kept, exactly as you read it.
7. Prefer what can be undone. Turn an app or a connection off rather than
   deleting it, unless the person asked for the deletion.
8. Saved changes usually reach live requests within a minute, and a block
   within ten seconds. See
   [When changes take effect](/how-it-works/apps-and-providers#when-changes-take-effect).
9. Do not send AI requests to test a setup unless asked: each one costs the
   person money.
10. An app's `warnings` name behaviour that will stop on a date. Tell the
    person about each one.

## CLI task workflow

1. Read `agw provider list --json` and `agw app list --json`. Reuse the IDs and
   slugs they answer. Look at an app with `agw app show <app> --json`.
2. For a missing provider, tell the person which one. Then:
   - If you run on the person's own machine, you may run
     `agw provider add --type <type> --browser --json` without `--no-open`.
     Read its stderr. If it says a browser window opened, tell the person to
     type the key there, and wait with `agw operation wait <id> --json`. If it
     says the link was saved to a file, the browser did not open: switch to the
     next bullet. Never tell the person a window opened unless `agw` said so.
   - Otherwise, ask them to add the key themselves: on the console's
     **Providers** page, or with `agw provider add --type <type>` on their own
     machine, which asks for the key in a hidden prompt. Then check
     `agw provider list` and carry on.

   Never ask for a key in the chat, and never read or pass on a browser step's
   link file.
3. Read the command's `--help`, then make the change. For a new app, check it
   first with `agw app add … --dry-run`. For an iOS app, use the person's Team
   ID and Bundle ID. A server app's key goes to the private file `agw` names, or
   a new path given with `--key-output`: `agw app add` creates the app directly
   and writes its key there, which is safe for a CLI agent.
4. To allow a provider on a new app, use `--providers <slug>` (its first
   provider operation) or `--providers <slug>=<op>+<op>`. `agw provider types`
   lists each provider's operations, and `agw model list` the priced models.
5. To change an existing app:
   - `agw app update <app> --name … --status …` changes only those.
   - For any other setting, `agw app update <app> --operations @patch.json
     --revision <n>`, with the revision from `app show`. The file is a JSON
     Patch: `add`, `replace` or `remove` at paths such as
     `/config/limits/per_app/requests/per_minute`.
   - To save a whole document, write `name`, `config` and `status` from
     `app show`, with your change and every setting you found there. Check it
     with `agw app validate <app> --config @app.json --json`; validation refuses
     a `revision`. Then add the `revision` from `app show` and save it with
     `agw app replace <app> --config @app.json`.
   - A stale revision is refused with `app_revision_conflict`: read the app
     again, apply the change on top, and repeat.
6. Run `agw app check <app> --json`. It tests no provider key, device, sign-in
   or subscription.
   - `ready` means the app is active and at least one connection its routes or
     presets use can be reached: one that is active, or, for a preset, a first
     connection turned off with an active fallback. It checks connection status
     only, not that a request will serve.
   - Read each connection's `status`, and tell the person about any that is
     `disabled` or `missing`.
   - `ready: false` means the app is turned off, or no connection can be
     reached: say which, and suggest turning the app or a connection on, or
     adding the missing connection.
7. Run `agw app snippet <app> --json` for example requests (see "Applications"
   for what it leaves out). The snippet is built from the settings and sends
   nothing, so it confirms nothing: only a successful app request does. Send
   one only when the person asked for a test; the snippet is a good starting
   point for it.
8. Report as described in "Reporting back". A pending step is pending, never
   done.

Commands not built into `agw` come from the gateway: `agw --help` lists them.
Use `--json --no-input` for every command. `--json` answers
`{schemaVersion: 1, ok: true, context, result}` or
`{schemaVersion: 1, ok: false, error}`, either with optional `notices`. Follow
`error.nextAction`.

- With `--json`, a removal runs only with `--yes`, even on a terminal. Pass it
  only once the person has agreed.
- `--help` prints text, not JSON.
- Exit codes: `0` done, `2` wrong command line, `3` gateway or network failure,
  `4` a state or decision stops it, `5` stopped waiting. Exit `0` can carry a
  pending step: check `state`.
- `agw operation wait <id>` waits 300 seconds, or `--timeout <seconds>`. A wait
  that times out cancels nothing: run it again. A browser sign-in that timed
  out cannot be picked up: start it again.
- A `newer_gateway` notice means the gateway has settings this `agw` does not
  know. They are kept when it saves; tell the person to update `agw` before
  changing them. After some refusals, a `version_mismatch` notice names which
  side to update.
- When the gateway changed a command since `agw` read it, `agw` may read the
  command list again and retry, or refuse with `tool_changed`. A command that
  needs a newer `agw` is refused with `cli_outdated`.

## MCP

The MCP server's tools run the same operations as the CLI and the API. A client
connects with OAuth on its own: the person approves it in their browser,
choosing the account and **Read only** or **Manage**. A management key as a
bearer token works too.

- Start with `get_account`. It names the account, the person, their role and
  the grant. A **Read only** grant refuses every change with
  `grant_insufficient`.
- Read before you write: `list_providers`, `list_apps`, `get_app`.
  `list_models` and `list_provider_types` name the priced models and each
  provider's operations.
- For a small change, use `patch_app`. With `operations` and the revision
  `get_app` answered, it changes only the paths you name. It also takes
  `name`, `status`, `team_id`, `bundle_id`, `attest_environments` and
  `verify_on` directly, with no revision. `update_app` replaces the whole
  document.
- A provider key is never a tool argument. `add_provider` takes `type` and
  `name`, and optionally `slug`, `baseUrl`, `pricing` and
  `cloudflareGateway: { accountId, gatewayId }`; other top-level fields are
  refused. `rotate_provider_key` takes the connection's `id` and `revision`.
  Each answers a link for the person; poll `get_operation` with the answer's
  `id` and stop at `completed` or `expired` (`denied: true` when declined).
  Never open the link yourself. On a Cloudflare add, the person enters the
  Cloudflare token, which is required, and the provider key, which is optional.
  A custom provider, listed paths and pinned Vercel serving providers are for
  the person, in the console.
- `add_app` takes `{ config: { name, config, status? }, handle? }`, and
  `add_app_key` takes `{ app, name, handle? }`: two calls each, see "Retrying
  creation safely". A new key is never in a tool answer: give the person
  `reveal_url`, while the answer has one.
- A field shown as `[redacted]` holds a secret. Never send that marker back.
  Have the person change that setting in the console or the CLI.
- A refusal is a tool answer marked as an error, with the gateway's code and the
  next step.

The full rules are in the server's `agw://guide` resource.

## The management API

For an integration without the CLI or MCP:

- Base address: `{API}`, which is `https://api.appaigateway.com`, or the
  self-hosted gateway's own. Every route is under `/v2/admin/`, with JSON bodies.
- Send the management key as `Authorization: Bearer agw_mgmt_…`. A key has its
  grant, `read` or `manage`, and no more than its owner's role. It never
  expires on its own.
- `GET /v2/admin/session` answers the account, role and grant. Call it first.
- The **Access** routes, for management keys, CLI sign-ins and MCP connections,
  need a person signed in to the console: they answer a key or token with
  `403 session_required`.

See [Use the API](/automation/api) for the routes.

## Errors

Every refusal is `{ "error": { "code": "…", "message": "…" } }`, with a `data`
object only for codes that need more.

| Status | Code | What to do |
| --- | --- | --- |
| 400 | `invalid_request` | Fix what `message` names |
| 400 | `pricing_not_configured` | A model has no price. Use a priced model, or have the person add a price |
| 400 | `app_revision_required` | Send the revision from your read |
| 401 | `auth_required` | The credential is missing, wrong or revoked |
| 403 | `grant_insufficient` | Ask the person for a **Manage** grant |
| 403 | `forbidden` | The person's role does not allow it |
| 403 | `session_required` | Only the person, in the console, can do this |
| 404 | `not_found`, `app_not_found`, `provider_not_found`, `key_not_found` | Nothing with this ID in the account |
| 409 | `app_revision_conflict` | Read it again and apply the change on top |
| 409 | `conflict` | On a change, read it again and apply the change on top. On a provider create, the slug is taken: choose another. On an app create, nothing was written: retry |

The errors apps get on their requests are in [Errors and limits](/integrate/errors).

## API workflow for setting up an app

1. `GET /v2/admin/providers`. Note each connection's `type` and `slug`.
2. If one is missing, ask the person to add its key themselves, on the
   console's **Providers** page or with `agw` on their own machine. Or open the
   step with `POST /v2/admin/provider-handoffs` (see "Providers"), give the
   person the link it answers, and poll `GET /v2/admin/operations/{id}`. That
   link is the console approval page the handoff returns for the person, so you
   may pass it on.
3. Compose the app from the reference below.
4. `POST /v2/admin/app-drafts/validate` with it. Fix every refusal.
5. Create it through a reserved create ("Retrying creation safely"). Do not use
   the plain `POST /v2/admin/apps`: for a server app it answers the first key in
   plain text, in the answer you read. The reserved create shows the key to the
   person on its reveal page instead.
6. `GET /v2/admin/apps/{app}/check`: read `ready` and each connection's
   `status`, as in the CLI workflow. Then `GET /v2/admin/apps/{app}/snippet`.
7. Report back.

## Providers

| Call | Body | Notes |
| --- | --- | --- |
| `GET /v2/admin/provider-types` | | Each type, its provider operations, and whether it can go through Cloudflare |
| `GET /v2/admin/providers` | | `providers[]`: `id`, `type`, `slug`, `name`, `status`, `secretHint`, `baseUrl`, `cloudflareGateway`, `passthrough`, `pricing`, `revision` |
| `POST /v2/admin/provider-handoffs` | `type` and `name`; optional `slug`, `baseUrl`, `pricing`, `cloudflareGateway: { accountId, gatewayId }` | Answers a link where the person types the key: through Cloudflare, the Cloudflare token (required) and the provider key (optional). Other fields are refused: a custom provider, listed paths and `servingProviders` are set in the console |
| `POST /v2/admin/providers/test` | `type`, `secret`, `baseUrl`, `cloudflareGateway`, `auth` | Tries a key without saving. Only `reason: "rejected"` says the key is probably wrong |
| `PUT /v2/admin/providers/{id}` | `revision` and any of `name`, `pricing`, `status`, `passthrough`, `servingProviders`, `baseUrl`, `cloudflareGateway`, and `auth` on a custom provider | `status: "disabled"` pauses it and keeps the key and slug. See below for changes that need a secret |
| `POST /v2/admin/providers/{id}/key-handoffs` | `revision` | A link where the person types a new key |
| `DELETE /v2/admin/providers/{id}` | | For good, with its prices. Apps that use it start failing |

Some provider changes need a secret in the same request, so leave them to the
person, in the console:

- a new base URL needs the provider key again;
- a new Cloudflare gateway needs its token, and the provider key or Cloudflare's
  stored keys, which the person chooses in the console;
- leaving Cloudflare needs the provider key.

Removing a base URL needs no secret, so you may do it: the stored key goes back
to the provider's own address.

The first connection of a type usually takes the type as its slug, such as
`openai`. Another one of the same type needs its own slug.

A model needs a price, from the price list (`GET /v2/admin/prices`) or the
connection's own `pricing`, unless the provider reports each request's cost.
See [Model pricing](/providers/model-pricing). Base URLs, custom providers and
listed paths are in [Custom base URLs](/providers/custom-base-urls), and
Cloudflare and Vercel AI Gateway in [their guide](/providers/gateways).

## Applications

| Call | Body | Notes |
| --- | --- | --- |
| `GET /v2/admin/apps` | | `apps[]` |
| `GET /v2/admin/apps/{app}` | | `{ app: { id, name, config, status, revision, created_at, updated_at, warnings? } }` |
| `POST /v2/admin/app-drafts/validate` | `{ name, config, status? }` | Checked as a new app. Saves nothing |
| `POST /v2/admin/apps/{app}/validate` | `{ name, config, status? }` | Checked as a change of that app. Saves nothing |
| `POST /v2/admin/apps` | `{ name, config, status? }` | Answers `app`, and for a server app its key in plain text. Agents use the reserved create instead |
| `PUT /v2/admin/apps/{app}` | `{ name, config, status?, revision }` | Replaces the whole app |
| `PATCH /v2/admin/apps/{app}` | `{ revision, operations }` | JSON Patch `add`, `replace` or `remove` under `/name`, `/status` or `/config` |
| `GET /v2/admin/apps/{app}/check` | | `ready`, and each connection the app's routing and presets name, with its `status`. `ready` is a connection-status check, not proof a request will serve |
| `GET /v2/admin/apps/{app}/snippet` | | Example requests for the app's routes and presets, with no credential in them |
| `DELETE /v2/admin/apps/{app}?confirm={app}` | | For good: its keys, users and App Attest keys go; its usage history stays |
| `GET /v2/admin/apps/{app}/keys` | | Server apps only |
| `POST /v2/admin/apps/{app}/keys` | `{ name }` | Answers the key once |
| `POST /v2/admin/apps/{app}/keys/{key}/revoke` | | |

`status` is `active` or `disabled`. A disabled app refuses every request with
`403 app_disabled`, and keeps everything.

The snippet leaves some things out, by design. A preset with fixed parameters
gets only a note with its URL, when its first connection is an active connection
the snippet can describe. A route or
preset whose connection is disabled or missing gets a note saying so, with no
example.

## Application configuration reference

`config` is one JSON object with five parts. Each part's guide explains its
choices; this is the shape.

```json
{
  "authentication": { … },
  "routing": { … },
  "limits": { … },
  "presets": { … },
  "conversations": { … }
}
```

Only `authentication` is required. A field left out takes its default. A key
the gateway does not know is refused. A key the gateway returned that you do
not know must be kept.

### `authentication`

An iOS app, `type: "apple_app_attest"`:

| Key | Meaning |
| --- | --- |
| `app_attest.team_id` | The Apple Team ID: ten uppercase letters or digits |
| `app_attest.bundle_id` | The bundle ID, in reverse-DNS form: at least two parts of letters, digits and `-`, joined by `.` |
| `app_attest.environments` | `["production"]` (the default), `["development"]`, or both |
| `app_attest.verify_on` | `every_request` (the default): every request carries `X-AppAttest-Proof`. `token_exchange`: only getting a token is checked |
| `end_user` | Required. `{ "source": "app_install" }` to count each install as a user, or `{ "source": "issuer", "issuer": { … } }` for signed-in users |

A server app, `type: "api_key"`:

| Key | Meaning |
| --- | --- |
| `end_user` | Required. `{ "source": "none" }` for no users; `{ "source": "header", "header": "x-end-user-id" }` when the server names the user; `{ "source": "issuer", "issuer": { … } }` for signed-in users |

`end_user.header` is a valid header name of at most 64 characters, and not one
the gateway uses: `authorization`, `cookie`, `host`, `content-type`,
`content-length`, `x-app-version`, `x-appattest-proof`, `x-client-sdk`,
`x-client-trace-id`, `x-conversation-storage`, or a built-in provider's key
header.

The `issuer` object. Every field is required unless marked Optional.

| Key | Meaning |
| --- | --- |
| `jwks_url` | Where the identity provider publishes its keys. `https` only |
| `issuer`, `audience` | Accepted `iss` and `aud` values: a non-empty string, or a non-empty list of them |
| `user_id_claim` | The claim used as the user ID, usually `"sub"` |
| `required_claims` | Claims a paid user must have, `[]` for none. Each has a non-blank `path` and exactly one of `contains` (a non-blank string, or a non-empty list of them) or `equals` (a non-blank string, a number or a boolean) |
| `max_token_lifetime_seconds` | A positive whole number. A token whose own lifetime is longer is refused. Usually `86400` |
| `token_header` | Optional. One more header that may carry the gateway token. Not empty, and not one of the names `end_user.header` may not be |
| `provider` | Optional: `firebase`, `supabase`, `auth0`, `clerk` or `custom`, so the console shows the same choice |
| `entitlement` | Optional: `revenuecat` or `custom`, for the same reason |

The settings for each identity provider are in
[User authentication](/applications/auth-policy/user-authentication). A
RevenueCat check is `{ "path": "revenueCatEntitlements", "contains": "<entitlement>" }`;
see [Subscription check](/applications/auth-policy/subscription-check).

### `routing`

| Key | Meaning |
| --- | --- |
| `providers` | Keyed by connection slug. A slug not listed is not allowed |
| `providers.<slug>.operations` | Required. The provider operations the app may use on that connection, such as `["openai.responses"]`. `passthrough` allows its listed paths |
| `providers.<slug>.models` | Optional. Allowed models. Left out, every priced model |
| `providers.<slug>.max_output_tokens` | Optional. A positive whole number: the most output tokens a request may ask for |
| `model_rewrites` | Optional. A model name the app sends, mapped to the model sent. The target needs a price |

See [Provider access](/applications/provider-access) and
[Model rewrites](/applications/model-rewrites).

### `limits`

Two parts, `per_user` and `per_app`, each with `requests` and `spending`. `null`
means no limit, and is the default.

| Key | Meaning |
| --- | --- |
| `requests.per_minute`, `requests.per_day` | A positive whole number, or `null` |
| `spending.monthly_nano` | A monthly budget in nano-dollars, from `0` to `9007199254740991`, or `null`. `1000000000` is $1; `0` stops all spend |
| `per_user.spending.scope` | Whose month a per-user budget counts. On iOS: `apple_account` (the default) or `install`, and `user` only with signed-in users. On a server app: `user` only. Only `per_user` has it |

`per_user` limits need an app whose `end_user.source` is not `none`. On an iOS
app, per-user request limits count per install. See
[Limits and blocking](/how-it-works/limits) and [Limits](/applications/limits).

### `presets`

Keyed by name. A preset serves without an entry for its connections in
`routing.providers`.

| Key | Meaning |
| --- | --- |
| `provider` | A connection slug |
| `operation` | The provider operation it sends, such as `openai.responses`. `agw provider types`, `list_provider_types` and `GET /v2/admin/provider-types` list candidates, but not every operation suits a preset (a job does not): validate the draft before choosing one |
| `model` | The model. Needs a price, unless the provider reports its cost |
| `params` | Optional. Merged into each JSON request, winning over the app's values. Refused on a preset that takes an upload, such as transcription |
| `max_output_tokens` | Optional. Refused where the operation has no output to cap |
| `fallback` | Optional. A list of `{ provider, model, operation? }` tried in order after no answer, a `429` or a `5xx`. Each speaks the same format. Left out, `operation` is the connection's first operation of that format that a preset can use |

See [Presets](/applications/custom-endpoints).

### `conversations`

Optional, and off unless `store` is `true`.

| Key | Meaning |
| --- | --- |
| `store` | Keep a copy of each eligible call whose answer went back to the app. A request with `X-Conversation-Storage: off` is skipped, and passthrough paths, jobs and live sessions are never kept. A body that is too large, or that holds a credential, may be left out |
| `keep.images`, `keep.audio`, `keep.files` | Which attachments are kept beside it. Each defaults to `true` |
| `retention_days` | Days to keep them, 1 to 400. Default `180` |

Turn it on only when the person asks, and remind them to say so in their privacy
policy. See [Conversation history](/applications/conversations).

### Names and lists

| Field | Rule |
| --- | --- |
| Connection slugs | `^[a-z0-9][a-z0-9-]{0,62}$` |
| Preset names | `^[a-z0-9-]{1,64}$` |
| Provider operation names | Not empty after trimming, at most 100 characters |
| Model names | Not empty after trimming, at most 200 characters |
| `operations`, `models` | When present, not empty, and no value twice |

### Examples

A server app whose backend names its users, with one OpenAI model:

```json
{
  "name": "Search service",
  "config": {
    "authentication": { "type": "api_key", "end_user": { "source": "header", "header": "x-end-user-id" } },
```

## Users and usage

- Users: `GET /v2/admin/apps/{app}/users` (`month`, `status`, `query`, `limit`,
  `offset`), `GET …/users/{user}`, `POST …/users/{user}/block` and
  `…/unblock`. Users an app's server names in a header cannot be blocked here.
  See [Users](/applications/users).
- Usage: `GET /v2/admin/usage` for the month across apps, and under
  `/v2/admin/apps/{app}`: `usage`, `usage/timeseries`, `usage/breakdown`,
  `charges` and `jobs`. See [Usage and charges](/applications/usage#through-the-api).
- Sign-in health: `auth-events/summary`, `auth-events` and `rejection-events`
  under the app. See [Auth events](/applications/auth-events).

## What clients send

You rarely call these, but you may write the code that does:

- A server app with no users: `Authorization: Bearer <app key>` on every
  request.
- A server app with signed-in users: `POST /v2/apps/{app}/auth/token` with
  `{ "api_key", "issuer_token" }`, then `Authorization: Bearer <access_token>`
  and `X-App-Version` on every request.
- An iOS app: App Attest sign-in, then the gateway token, `X-App-Version` and,
  where `verify_on` is `every_request`, `X-AppAttest-Proof`. The Swift package
  for this comes with the v2 SDK; until then, see [iOS apps](/integrate/ios).

See [Server applications](/integrate/server) and
[Calling the provider proxy](/integrate/proxy).

## Contacting human support

Where the gateway offers human support, you can write to it for the person:
`agw support send`, `contact_support` over MCP, or `POST /v2/admin/support`.
Support replies to the person's email address, never to you.

1. Only when the person asked. Show them the exact message first, and send it
   once they agree. Without a terminal, `agw support send` needs `--yes`.
2. Choose the type, `--type` on the CLI and `kind` over MCP and the API: `bug`,
   `support` for a question, or `feedback`.
3. Say what happened, what they expected and what was tried, with IDs and
   codes in `--context key=value`.
4. Never include a key, token or password: a message that looks like it holds
   one is refused, and nothing is sent.
5. Tell the person the answer's `reference`. The same message sent again within
   ten minutes sends nothing new.

```sh
agw support send --type bug --message "Streaming from my-app stops after about 30 seconds since Monday." \
  --context app_id=my-app --yes --json --no-input
```

## Reporting back

When you finish, report what you created or changed, by ID and slug; the URLs
the app calls; where each key was stored, or which reveal page the person must
open; any connection the check found disabled or missing; and what you could
not do. Never include a secret.

## Retrying creation safely

A plain create is not safe to repeat: if its answer is lost, you cannot tell
whether it happened. Over MCP and the API, create apps and app keys with a
reserved create:

1. `POST /v2/admin/reserved/apps` with `{ name, config, status? }`, or
   `POST /v2/admin/reserved/apps/{app}/keys` with `{ name }`. Nothing is
   created. The answer has `state: "reserved"`, a `handle`, the pending step's
   `id` and when it lapses, 15 minutes later.
2. Send the same body again with `handle`. It is created once, and the answer
   has `state: "created"`. Within 15 minutes of the creation, sending it again
   repeats that answer with `replayed: true`. Later it is refused with
   `already_completed`: keep the operation's `id` from step 1, and read
   `GET /v2/admin/operations/{id}` for what was created. If you reserve again,
   the new reservation may answer a `notice` naming an identical request:
   inspect that operation before you send the new `handle`, because sending it
   can create a duplicate.

A server app's key is never in these answers. While it can still be revealed,
the answer has `reveal_url`: give it to the person, where an owner or admin
sees the key once, within 15 minutes. Once the key is revealed, a repeated
answer may leave `reveal_url` out.

`GET /v2/admin/operations/{id}` says where a pending step stands: `pending`,
`completed` with what it created, or `expired`, with `denied: true` when the
person declined. Stop polling at `completed` or `expired`. The record is kept
for 90 days.

Refusals: `operation_mismatch` when the handle was reserved for other
arguments, `operation_expired` when it lapsed, and `operation_not_found` for a
handle this gateway never gave out.

A provider connection is added by the person, with its key, so it needs no
reserved create.
