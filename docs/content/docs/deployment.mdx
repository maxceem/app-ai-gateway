## The one secret you must supply

Provider credentials are added per organization in the console, not at deploy
time. The deployment itself needs exactly one operator-supplied secret: the key
that encrypts those credentials at rest.

| Value | Purpose |
|---|---|
| `SECRET_VAULT_LOCAL_KEK_V1` | Key encryption key for the self-hosted vault. Generate with `openssl rand -base64 32`. |

`JWT_SECRET` and `BETTER_AUTH_SECRET` are generated for you on first deployment.

<Callout type="warn" title="Back the vault key up">
  Losing `SECRET_VAULT_LOCAL_KEK_V1` makes every stored provider credential
  permanently unreadable. There is no recovery path; re-adding the keys in the
  console is the only fix.
</Callout>

## Secret vault modes

The vault mode is explicit — nothing is inferred from which secrets happen to be
present, and a missing or mixed configuration is a hard error rather than a quiet
fallback.

| `SECRET_VAULT_MODE` | Requires | Use it when |
|---|---|---|
| `local` (default) | `SECRET_VAULT_LOCAL_KEK_V1`, optional `SECRET_VAULT_LOCAL_KEK_V<n>` and `SECRET_VAULT_LOCAL_KEK_CURRENT_VERSION` | Self-hosting. AES-256-GCM in the Worker under a key you hold. No second service to run. |
| `kms` | `SECRET_VAULT_KMS_URL`, `SECRET_VAULT_KMS_TOKEN` | Hardened deployments. Envelope encryption through a [cf-kms](https://github.com/maxceem/cf-kms) worker in a separate security account, so the root key never enters this account and every decrypt is audited and revocable. |

Setting a variable belonging to the *other* mode is also an error: a
`SECRET_VAULT_LOCAL_KEK_V1` present in `kms` mode is a configuration mistake, not
something to ignore. A broken vault is visible immediately — `/v1/healthz`
reports a non-secret `vault` field:

```json
{ "ok": true, "service": "app-ai-gateway", "vault": "ok" }
```

`"vault": "misconfigured"` means every credential-touching request will fail with
`provider_unavailable`; the structured Worker log names the offending binding.

### Running kms mode

Deploy a cf-kms instance dedicated to this service (`cf-kms-app-ai-gateway`) in your
security account, on a custom domain, with its own `KEK_V1` and a `CALLERS` entry
of `{ "name": "app-ai-gateway", "requiredContext": { "service": "app-ai-gateway" } }`.
Then set `SECRET_VAULT_MODE=kms` plus the URL and caller token on this Worker.
Blobs are self-describing by prefix (`local1.…` versus `cfkms-env1.…`), so
switching modes is a decrypt-and-re-encrypt migration and a mismatch fails loudly
rather than silently.

## Deploy to Cloudflare

The repository's deploy button is the shortest interactive path. Cloudflare forks
the repository, provisions the Worker and compatible bindings, applies migrations,
and connects subsequent pushes to Workers Builds. The form asks only for the
vault key above.

## Deploy with Wrangler

From a clean checkout:

```sh
pnpm install
cp .dev.vars.example .dev.vars
openssl rand -base64 32   # paste into SECRET_VAULT_LOCAL_KEK_V1
```

Then run:

```sh
pnpm run secrets:upload
pnpm run deploy
```

The deploy command preserves existing secrets, creates missing JWT and Better
Auth signing secrets, provisions D1 when necessary, applies migrations by binding
name, and deploys the console and API.

The public `wrangler.jsonc` intentionally has no custom production domain or
Cloudflare account-specific D1 database ID. Those belong in a deployment
profile.

## Deployment profiles

A profile is a gitignored `wrangler.<profile>.overlay.jsonc` in the repository
root holding only the keys that differ from `wrangler.jsonc`. It is not a
complete Wrangler configuration: every command merges it over the tracked file
first, so shared sections such as Durable Object migrations are never duplicated.
Objects merge recursively, an array replaces the base array, and `null` removes
a key.

```jsonc title="wrangler.prod.overlay.jsonc"
{
  "workers_dev": false,
  "routes": [{ "pattern": "console.example.com", "custom_domain": true }],
  "vars": { "SECRET_VAULT_MODE": "kms", "SECRET_VAULT_LOCAL_KEK_CURRENT_VERSION": null },
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "app-ai-gateway-prod",
      "database_id": "00000000-0000-0000-0000-000000000000",
      "migrations_dir": "migrations"
    }
  ]
}
```

```sh
pnpm run deploy --profile prod
pnpm run deploy:dry-run --profile prod
pnpm run db:migrate --profile prod
```

The merged result is written to `wrangler.<profile>.generated.jsonc`, also
ignored, and handed to Wrangler with `--config`. A profile's first deployment
uploads operator secrets from `.dev.vars.<profile>` when that file exists. Keep
overlays out of version control; they are the only place account identifiers,
domains, and service bindings should live.

### Google OAuth from changing preview hosts

Google requires an exact OAuth callback URL and does not accept wildcard
subdomains. To let local or preview instances use one Google OAuth client, set
`OAUTH_PROXY_PRODUCTION_URL` to the stable deployed origin and configure the
same dedicated `OAUTH_PROXY_SECRET` in that deployment and each participating
local environment. Keep `BETTER_AUTH_SECRET` different between environments.

Register only this callback with Google:

```text
<OAUTH_PROXY_PRODUCTION_URL>/v1/auth/callback/google
```

The stable deployment exchanges the Google code and relays a short-lived,
encrypted profile to the originating instance. The originating instance writes
the user and session to its own database; the stable deployment does not write
the preview user to its database.

## Rate limiting

The gateway does not throttle authentication attempts itself, and cannot do it
usefully: a Worker's memory is per isolate, so an in-memory counter — including
Better Auth's built-in rate limiter — sees only a fraction of the traffic and
limits nothing in practice. Bounding password guessing and challenge flooding is
the deployment's job, with [Cloudflare rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/)
on the zone in front of the Worker. Those counters live at the edge, so they hold
across isolates and colocations, and a refused request never reaches the Worker
at all.

Create three rules, each counting by client IP:

1. **Operator sign-in** — 10 requests per minute, block for 10 minutes. This is
   the console's password endpoint and the one route where guessing pays.

   ```txt
   http.request.uri.path eq "/v1/auth/sign-in/email"
   ```

2. **Account creation and password reset** — 5 requests per minute.

   ```txt
   http.request.uri.path matches "^/v1/auth/(sign-up|forget-password|reset-password)"
   ```

3. **Application authentication** — 60 requests per minute. These routes are
   unauthenticated by design; a legitimate app performs a handful of them per
   hour per device, so the limit is far above real use and still bounds a flood.

   ```txt
   http.request.uri.path matches "^/v1/apps/[^/]+/auth/(challenge|token|register)$"
   ```

Rate limiting rules exist on every plan, but not in equal amounts, so adapt
rather than skip:

- The free plan allows **one** rule, with a fixed ten-second counting period and
  a ten-second block. Spend it on sign-in, at 2 requests per ten seconds.
- The `matches` operator needs a Business plan or above. On Free and Pro, write
  rules 2 and 3 without a regular expression:

  ```txt
  http.request.uri.path in {"/v1/auth/sign-up/email" "/v1/auth/forget-password" "/v1/auth/reset-password"}
  ```

  ```txt
  starts_with(http.request.uri.path, "/v1/apps/") and (ends_with(http.request.uri.path, "/auth/challenge") or ends_with(http.request.uri.path, "/auth/token") or ends_with(http.request.uri.path, "/auth/register"))
  ```

The rules belong to a zone, so a deployment reachable only on `workers.dev` has
nowhere to put them. That is one more reason to serve the gateway on a custom
domain through a deployment profile.

## Verify

Call the deployed health endpoint and then sign in to the console:

```sh
curl https://YOUR-WORKER.workers.dev/v1/healthz
```

Confirm `"vault": "ok"` before adding provider credentials.

Create the initial operator with `/v1/auth/sign-up/email`, then set
`ALLOW_PUBLIC_REGISTRATION=false` for a private deployment. Admin automation uses
organization-scoped `agw_mgmt_` keys created under `/v1/admin/keys`.

Finally, add provider credentials under **Providers** in the console — see
[Providers](/providers). Until an organization has a credential for a
provider, its requests answer `502 provider_not_configured`.

<Callout type="warn" title="Migration state is separate from Worker versions">
  A Worker rollback does not roll back D1. Review new migrations before deploying
  them to shared environments and never modify an applied migration.
</Callout>
