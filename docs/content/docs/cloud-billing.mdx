title: Cloud billing setup
description: Connect the optional billing worker and enforce plan entitlements.
---

The open-source default has no `BILLING` binding. In that mode the gateway marks
access as self-hosted and does not impose subscription entitlements.

## Add the service binding

Hosted operators can bind the `BillingWorker` entrypoint from a deployed
`cf-billing` service in the environment that needs billing:

```jsonc
{
  "services": [
    {
      "binding": "BILLING",
      "service": "YOUR-BILLING-WORKER",
      "entrypoint": "BillingWorker"
    }
  ]
}
```

Do not add this binding to an OSS/self-hosted environment unless it has a
corresponding billing service. The console discovers availability from
`GET /v1/console/capabilities`.

The gateway always calls billing with service ID `app-ai-gateway` and the current
operator organization ID as the tenant ID. Create matching service and plan data
in the billing worker before enabling the binding.

## The plan's request allowance

A plan carries exactly one limit, and it is the gateway's only quota:

```json
{ "maxRequestsPerMonth": 100000 }
```

It is a whole, non-negative count of requests the organization may have
dispatched to a provider within one UTC calendar month, shared by every
application, credential and end user it owns. A plan that omits the key leaves
the organization unlimited. The value may be written as a number or as a JSON
string; anything else — a fraction, a negative, `null` — is a plan
misconfiguration, and the gateway answers `502 billing_unavailable` rather than
guess an allowance.

Nothing about a stored application configuration is capped by a plan. Creating,
validating, and updating apps are entitlement checks only.

See [Operations](/docs/operations) for what a client sees when the allowance runs
out.

Inactive organizations receive `402 payment_required` on their apps' data-plane
routes. Billing RPC failures also fail closed, but under a different code: an
unreachable billing service says nothing about the subscription, so the gateway
answers `503 billing_unavailable` with a short `Retry-After` instead. Clients
should treat the first as something the customer has to act on and the second as
worth retrying. Neither condition deletes or disables application records, so
access resumes when billing becomes active again.

`GET /v1/admin/billing/status` reports the month against the allowance beside
the subscription, as `quota`:

```json
{ "month": "2026-09", "used": 41288, "limit": 100000, "resetAt": "2026-10-01T00:00:00.000Z" }
```

`limit` is absent on a plan that sets no ceiling, and `quota` is `null` on a
self-hosted deployment. The console renders it on the billing page and warns
above every page once four fifths of the allowance is spent.

Owners and admins use `/v1/admin/billing/*` for plan listing, checkout, plan
changes, cancellation, resume, trials, and status. Members retain read-only
access to status and plan information.
