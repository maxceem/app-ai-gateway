---
title: Updating
description: Pick up new releases, understand what a deployment changes, and handle database migrations safely.
---

How you update depends on how you deployed. Every route preserves your secrets,
applies any new database migrations, and redeploys the Worker together with its
console.

## CLI deployments

A gateway installed with `agw deployment setup` is updated by the CLI itself:

```sh
npm install -g @maxceem/agw
agw deployment update --dry-run
agw deployment update
```

Each CLI version installs exactly one gateway build, so picking up a new release
means installing the newer CLI. It downloads that build once from the project's
GitHub release, checks it against a SHA-256 built into the CLI, and caches it
under `~/.cache/agw`; `--release-archive <path>` uses a copy you downloaded
yourself instead, for a machine with no route to GitHub. The dry run reports the
version it would move to and changes nothing. The update applies any new
migrations and then deploys.

## Button deployments

The one-click flow forked the repository into your GitHub account and
connected the fork to Workers Builds. Every push to the connected branch
triggers a build and a deploy. The deploy command Workers Builds runs is the
repository's `deploy` script, the same one a checkout uses, so migrations are
applied as part of it. You can see and change it under the Worker's
**Settings → Build**.

To pick up a new release, bring the upstream changes into your fork and push:

```sh
git clone https://github.com/YOUR-ACCOUNT/app-ai-gateway
cd app-ai-gateway
git remote add upstream https://github.com/maxceem/app-ai-gateway
git fetch upstream
git merge upstream/main
git push
```

Watch the build under the Worker's **Deployments** in the Cloudflare
dashboard. When it finishes, check the health endpoint as after the first
deployment:

```sh
curl https://YOUR-WORKER.workers.dev/v1/healthz
```

Plain variables changed only in **Settings → Variables** can be overwritten
by the next deploy. Preserve them in the deployment configuration, or use
[Wrangler's `keep_vars`](https://developers.cloudflare.com/workers/wrangler/configuration/)
when you intentionally manage them in the dashboard. Existing secrets are kept.

## Wrangler deployments

Pull the release into your checkout and deploy again:

```sh
git pull
pnpm install
pnpm run deploy
```

Add `--profile <name>` when the deployment uses a
[profile](/self-hosting/deploy-with-wrangler). To see what a release would
change before deploying it, run the dry run first:

```sh
pnpm run deploy:dry-run --profile prod
```

The deploy script checks that the vault secret still exists, leaves
`JWT_SECRET` and `BETTER_AUTH_SECRET` as they are, applies migrations, and
deploys. App and provider configuration stays in the database. Plain Worker
variables come from the deployment configuration, so preserve dashboard-only
changes there before deploying.

Console build variables such as `VITE_POSTHOG_KEY` are read when the console
is built, so a change to one of them also needs a deploy.

## Release promotion and established sessions

The button, checkout deploy command, and CLI share the same release sequence:
build and check the artifacts, acquire one deployment lease, apply compatible
migrations, deploy the stable gateway at 100%, verify its exact build and
required storage bindings, create or reuse an immutable realtime Worker,
verify it, and atomically promote the URL new connections discover. Updates
keep the selected gateway name, database, and deployment identity.

An update that fails preparation or health verification keeps the previous
realtime pointer. Retry the same command after fixing the reported failure.
Overlapping updates are refused while a deployment holds the lease; an
interrupted deployment's lease expires after ten minutes. The first checkout
installation may provision the gateway and database before it can acquire this
lease. It establishes its deployment identity before creating secrets, so an
interrupted first installation can retry against that same identity.

An existing older gateway without `DEPLOYMENT_ID` cannot report a verifiable
release version. First establish a stable plain-text `DEPLOYMENT_ID` on that
reviewed supported deployment using its existing deployment method, then retry.
Never change an established identity.

Retired realtime Workers refuse new sessions after 60 seconds and retain
established sessions and pending usage recovery. They are kept for the maximum
30-minute session, that admission grace, seven days of recovery, and one hour
of margin. Expired releases are cleaned up on subsequent deployments. An idle
installation retains them until you deploy again or run cleanup:

```sh
agw deployment cleanup
# From a checkout:
pnpm run deploy cleanup --profile prod
```

Deployment output reports the previous main version and recorded build ID.
To return to a retained compatible deployment, use that build ID:

```sh
agw deployment rollback --release-id PREVIOUS-BUILD-ID
# From a checkout:
pnpm run deploy rollback PREVIOUS-BUILD-ID --profile prod
```

Rollback restores the recorded main version and realtime routing together,
reactivates the old realtime release, and restarts retirement eligibility for
the release it replaces. It never rolls back database data. Missing releases
or incompatible backend, schema, or Durable Object lifecycle declarations stop
rollback. Keep the deployment configuration and vault key backed up securely.
Use these commands instead of independently rolling back a Worker in the
dashboard, which does not coordinate realtime routing.

`/v1/healthz` reports the main build ID, current realtime release ID, backend
contract, and readiness. Health checks use no AI provider and consume no app
request allowance. HTTP API URLs stay stable; in-progress HTTP streams are
still subject to Cloudflare's own deployment and network behavior.

## Database migrations

Migrations live in the `migrations` directory and are applied by the deploy
script through the `DB` binding, so a deployment does not depend on a
particular database name. You can also apply them on their own:

```sh
pnpm run db:migrate
pnpm run db:migrate --profile prod
```

Applying is idempotent. A migration that has already run is skipped, so
running the command twice is harmless.

<Callout type="warn" title="A Worker rollback does not roll back the database">
  Cloudflare can roll a Worker back to a previous version, but the database
  keeps every migration that has been applied. Rolling back to a version that
  predates a migration leaves the code and the schema out of step. Review the
  migrations a release brings before deploying it to a gateway your apps
  depend on, and never edit a migration that has been applied.
</Callout>

Keep migrations additive while a retired realtime runtime may still call the
stable gateway. Expand the schema and backend contract first; remove old fields
or methods only after all retained runtimes and recovery work are gone. The
release compatibility declarations are reviewed by contributors, not inferred
by a SQL parser, so they do not prove an arbitrary custom migration safe.

A safe routine for a release that includes migrations:

1. Read the new files under `migrations` and confirm they only add what the
   release needs.
2. Deploy to a second gateway first if you run one, for example a staging
   profile with its own database.
3. Deploy to the gateway your apps use, then check `/v1/healthz` and send one
   request through an app.

## Updating from v0.3.0 or earlier

v0.4.0 changed the database layout and cannot update an existing v0.3.0 or
earlier gateway in place. `agw deployment update` refuses such an update and
changes nothing. Current button and checkout releases check the deployed version before updating. Do not
point an older deployment script at v0.4.0. Deploy v0.4.0 as a fresh gateway instead, and recreate
your apps, keys and provider credentials there. If you
need help moving data from an existing installation,
[open an issue on GitHub](https://github.com/maxceem/app-ai-gateway/issues).

## For contributors

Change the schema definition, run `pnpm run db:generate` to produce the
migration file, and commit both the schema change and the generated migration
together. Never modify a migration that a deployment has already applied; add a
new one instead.

## Checking a checkout

Before deploying a change of your own, run the same checks the project runs:

```sh
pnpm run verify
pnpm run deploy:dry-run
```

`verify` type-checks every project, checks the generated OpenAPI document for
drift, and runs the Worker, console, CLI and script tests. The dry run builds the console and resolves
the Wrangler configuration without deploying anything.
