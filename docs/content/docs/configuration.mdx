An application row is the only tenant-specific input. Do not add tenant branches
to Worker code.

## Application limits and the plan allowance

The gateway has two quotas. They constrain different people, are set by
different people, and are easy to read as one thing when they are not.

|  | **Plan allowance** | **Application limits** |
| --- | --- | --- |
| Who it limits | Your organization | Your application's end users |
| Who sets it | Your billing plan | You, in `config.limits` |
| Scope | Every app, key and user you own | One user, or one app |
| Refusal | `billing_request_quota_exceeded` | `app_rate_limited`, `app_budget_exhausted` |

Neither constrains the other. A large plan does not stop you capping your own
users at ten requests a minute, and a user well inside your limits is still
refused once your organization's allowance runs out. Application limits are
checked first, so a request your own limits refused never spends the allowance
you are billed for.

The allowance is documented in [Operations](/operations); everything below
is yours to set.

## Application IDs

The ID is the `{app}` segment of every URL the app uses, it is unique across the
whole deployment, and it cannot be changed once the app exists — clients compile
it into their base URL.

Omit `id` when creating an application and the gateway assigns one: the name,
slugified, plus a six-character random suffix (`Calorie Tracker` becomes
`calorie-tracker-k3f9x1`). Every generated ID is suffixed, including the first
one on an empty deployment, so no organization can claim a bare name that others
then have to work around. The response's `app_id` is the assigned ID, and the
console shows it before you create the app.

Send an `id` and it is used exactly as given, or the request is refused —
`409 app_id_taken` if another application already holds it, `400` if it is on
the small reserved list (`admin`, `console`, `new`, `v1`, and similar). A
requested ID is never silently replaced with a different one.

The ID is not a secret: it travels in every client URL. It is also not a
credential — App Attest or an API key still has to pass.

## Server application

Use API-key authentication for a trusted backend:

```json
{
  "name": "Search service",
  "config": {
    "authentication": {
      "type": "api_key",
      "end_user": {
        "header": "x-end-user-id",
        "required": false,
        "fallback": "api_key"
      }
    },
    "routing": {
      "providers": {
        "mode": "selected",
        "selected": {
          "openai": {
            "allowed_paths": ["v1/responses"],
            "allowed_models": ["gpt-5.6-terra"],
            "max_output_tokens": 4096
          }
        }
      },
      "model_rewrites": {}
    },
    "limits": {
      "per_user": {
        "requests": { "per_minute": 30, "per_day": 1000 },
        "spending": { "monthly_usd": 10 }
      },
      "per_app": {
        "requests": { "per_minute": 300, "per_day": 10000 },
        "spending": { "monthly_usd": 100 }
      }
    }
  }
}
```

Creating an API-key application returns its initial plaintext key once. Store it
immediately in the calling application's secret manager.

The keys of `routing.providers.selected` are **provider instance slugs**, not
provider types, so `"openai"` above means the instance reachable at
`/proxy/openai/…`. Naming `"openai-dev"` instead restricts the app to that
second key. `mode: "all"` keeps its meaning: any instance the organization has
configured. See [Providers](/providers).

Slugs are checked when a configuration is written, and the rule differs between
creating and updating an application:

- **Create** — every slug named by `routing.providers.selected` and by any
  endpoint target must belong to an active instance of the organization.
- **Update** — only slugs the request *introduces* must exist. A slug the
  stored configuration already names stays writable even after its provider is
  deleted, so removing a credential never blocks unrelated edits to the apps
  that mention it.

A dangling slug is not silently repaired: requests routed to it keep failing
with `502 provider_not_configured` until you re-create the instance or drop the
reference. `POST /v1/admin/apps/{app}/validate` applies the same rule as the
write it previews.

`model_rewrites` targets are model names rather than instance references, so
they are priced against the shipped catalog for any provider type plus any
instance's own overrides — an organization with no providers configured yet can
still save an application that rewrites models.

## Limits

`limits` is optional. Omit it and the application is unlimited; every field is
independently nullable, and `null` means unlimited for that field alone.

`per_user` applies to each authenticated end user separately. `per_app` is one
budget shared by every user and credential of the application at once.

```json
"limits": {
  "per_user": {
    "requests": { "per_minute": 30, "per_day": 1000 },
    "spending": { "monthly_usd": 10 }
  },
  "per_app": {
    "requests": { "per_minute": null, "per_day": null },
    "spending": { "monthly_usd": 100 }
  }
}
```

Rate limits answer `429 app_rate_limited`; an exhausted budget answers
`429 app_budget_exhausted`. Both carry a `Retry-After` header and a
`data.scope` of `"user"` or `"app"` saying which of the two refused — worth
telling apart in a client, because an `"app"` refusal is somebody else's traffic
and backing off this one user will not clear it.

Four things to know before you rely on them:

- **Rate windows are fixed, not sliding.** A caller can spend a full minute's
  allowance at the end of one minute and again at the start of the next, so a
  burst of up to twice `per_minute` is possible across a boundary. Days roll at
  UTC midnight.
- **Budgets are settled after the fact.** A request's cost is known only once
  its response completes, so a budget refuses the request *after* the one that
  crossed it. A single very expensive call can overshoot. Turning an app-wide
  budget on part-way through a month backfills from the month's usage, so it
  counts what has already been spent rather than starting from zero.
- **Edits take up to a minute** to reach every isolate, because application
  configuration is cached for 60 seconds.
- **`monthly_usd: 0` is a closed door, not "unlimited".** Use `null` for
  unlimited. A request limit of `0` is rejected outright as a likely typo, but a
  budget of zero is a legitimate way to stop all billable traffic for a scope.

`per_user` limits on a server application need care. Unless the backend sends
`x-end-user-id`, every request shares one identity — the API key's own id — so a
per-user limit caps the whole backend rather than metering its users. The
console leaves `limits` unset when you create a server application for exactly
this reason. Use `per_app` there, or send a real end-user id.

Blocking a user is a separate switch and is not a limit: it is immediate, and it
answers `403 auth_required`. See [Operations](/operations).

A caller can read its own standing with `GET /v1/apps/{app}/me`, which returns
the per-user limits, the day's request count, what is left of it, and the
month's spend. Requests are only counted while a per-user limit is set — an
application with none never reaches the counter — so `requests_today` is `null`
rather than `0` on such an app. The organization's plan allowance is deliberately not reported
there: it is your arrangement with the gateway, not your users' business.

Add an `issuer` block beside `end_user` when the trusted client acts for real
users. In that mode the key is client proof only: exchange it with an issuer JWT
at `/v1/apps/{app}/auth/token`, then use the returned gateway token on data-plane
requests.

An issuer block always carries `jwks_url`, `issuer`, `audience`, `user_id_claim`,
`required_claims` and `max_token_lifetime_seconds`. `issuer` and `audience` are
required — each one string or a list of accepted alternatives — because issuers
such as Firebase, Sign in with Apple and Google Sign-In publish one key set for
every customer, so without them a token minted in someone else's project
verifies against your application. See
[Authentication](/authentication#scoping-an-issuer-to-your-tenant) for the
value each provider expects.

## Named endpoints

An optional top-level `endpoints` block moves the provider, model, and fixed
parameters out of the client and behind a slug. See
[Named endpoints](/named-endpoints).

## Validation workflow

Use the console for guided editing. Automation should validate a candidate through
`POST /v1/admin/apps/{app}/validate` before updating the stored configuration.
The generated API reference describes the canonical request schema.
