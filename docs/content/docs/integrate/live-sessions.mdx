---
title: Live sessions
description: Open a voice or other live session through the gateway's relay, keep it alive, come back after a dropped network, and read the close codes.
---

A live session is a long WebSocket conversation with a provider, such as a
voice session. Your app does not connect to the provider. It asks the gateway
for a session, and the gateway answers with a short-lived **ticket** and the
address of its **relay**. The app opens a WebSocket to the relay with the
ticket, and the relay connects to the provider with your provider key. The key
never reaches the device.

The relay passes the provider's own messages through both ways, as they are.
Your app speaks the provider's protocol, exactly as it would to the provider.
The relay adds a few small messages of its own, all starting with
`{"type":"agw.`, to keep the session alive and to come back after a dropped
network.

These providers are served today:

| Provider | Live-session path | Model |
| --- | --- | --- |
| OpenAI Realtime | `v1/realtime` | for example `gpt-realtime-2.1` |
| OpenAI Realtime over WebRTC | `v1/realtime/calls`. See [OpenAI Realtime over WebRTC](#openai-realtime-over-webrtc) | for example `gpt-realtime-2.1` |
| xAI voice | `v1/realtime` | for example `grok-voice-3.0` |
| Gemini Live | `ws/google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContent` (or `v1alpha`) | for example `gemini-3.1-flash-live-preview` |
| OpenAI GPT-Live | `v1/live/sessions` | `gpt-live-1` |
| ElevenLabs text to speech | `v1/text-to-speech/{voice_id}/stream-input` | for example `eleven_flash_v2_5`; `eleven_multilingual_v2` when none is named |
| ElevenLabs agents | `v1/convai/conversation` | the agent's id, such as `agent_7201m7pd…`. See [ElevenLabs agents](#elevenlabs-agents) |
| Deepgram speech to text | `v1/listen` | for example `nova-3`, the gateway's default when none is named |
| A custom provider | the WebSocket path you list | none. See [A live provider the gateway doesn't know](#a-live-provider-the-gateway-doesnt-know) |

Text to speech and speech to text streams have their own limit on open
sessions, apart from voice conversations. At that limit a new stream is
refused, since the app may still be playing or reading the one before.

The app's settings must allow the operation, as for any call. See
[Provider access](/applications/provider-access). Live sessions need a
connection that goes straight to the provider: a connection set up through
Cloudflare AI Gateway gets `502 provider_unavailable`.

## Starting a session

Ask the gateway for a session with the app's usual credentials:

```http
POST /v2/apps/{app}/sessions/{provider}
Content-Type: application/json

{"path": "v1/realtime", "model": "gpt-realtime-2.1"}
```

- `{provider}` is the connection's slug, such as `openai`.
- `path` is the provider's own live-session path from the table above. For
  ElevenLabs and Deepgram streams and ElevenLabs agents, put the provider's own
  options in its query, such as `v1/listen?encoding=linear16&sample_rate=16000`,
  the model too if you like (`model`, `model_id`, an agent's `agent_id`) when
  the body names none. They go to
  the provider as they are, except the model, which is always the session's,
  and fields that would send results elsewhere or carry a credential (a key,
  a token or an authorization), which are removed. Other sessions take no
  query: a path with one gets `403 path_not_allowed`.
- `model` is the model the session runs. The relay keeps the session on this
  model, whatever the app sends later.
- `takes_over` (optional) names an earlier session of the same user that this
  one replaces. See [When to start a new session](#when-to-start-a-new-session).

The answer:

```json
{
  "session_id": "…",
  "ticket": "…",
  "relay_url": "wss://…",
  "expires_at": "…",
  "ends_at": "…"
}
```

Open a WebSocket to `relay_url` within a minute, with these headers:

- `Authorization: Bearer <ticket>`. The ticket goes only in this header, never
  in a URL.
- `x-agw-relay-messages: 1`, to get the relay's messages described below.
  Without it, the relay sends only the provider's messages, which suits an
  official provider SDK, but then a dropped network always means a new
  session.

The session lasts at most until `ends_at`, 30 minutes after it starts.

In Swift, the package does all of this:

```swift
let ticket = try await client.startOpenAIRealtimeSession(model: "gpt-realtime-2.1")
let session = LiveSession(ticket: ticket)
await session.start()
for await event in session.events {
    switch event {
    case .started: break              // send the provider's first messages
    case .text(let json): handle(json) // a provider message
    case .data(let bytes): play(bytes) // a binary provider message
    case .reconnecting, .resumed: break
    case .ended(let code, let reason): finish(code, reason)
    }
}
```

`startXAIVoiceSession(model:)` and `startGeminiLiveSession(model:)` work the
same way. For Gemini Live, send Gemini's `setup` as the first message, as
usual.

## The relay's messages

From the relay:

- `{"type":"agw.session.started","reconnect_secret":"…","deadline":…}` once
  the session has started, before any provider message. Keep the secret in
  memory; it brings the app back to this session after a dropped network.
- `{"type":"agw.session.resumed","deadline":…}` when the app came back to the
  same session.
- `{"type":"agw.heartbeat"}` in answer to each heartbeat.

From the app:

- `{"type":"agw.heartbeat"}` after 30 s without sending anything else.
- `{"type":"agw.received","bytes":N}` every few seconds while provider
  messages arrive, and once more after they stop. `N` is the total received
  on the current link, since `agw.session.started` or `agw.session.resumed`:
  text counts as its length in UTF-16 units
  (`String.utf16.count` in Swift), binary as its bytes. The relay's own
  messages don't count.
- `{"type":"agw.reconnect","secret":"…"}` as the first message on a new link,
  when coming back.

Write each one exactly like this: starting with `{"type":"agw.`, with no
space, and `type` first. The relay keeps these to itself and passes anything
else to the provider.

## Staying alive

- **The heartbeat.** The relay ends a session when nothing has come from the
  app for 90 s (`heartbeat_timeout`). An app that only listens sends the
  heartbeat to stay. The relay answers each heartbeat at once, so an app that
  gets no answer within about 10 s knows its link died without a word, and
  comes back on a new link.
- **Keeping up.** An app that falls about 30 s behind what the relay sent is
  ended (`client_too_slow`). Sending the received-byte reports, and reading
  messages as they come, keeps a slow network from being mistaken for a stuck
  app.
- **Quiet providers.** Some providers never end a quiet session on their own.
  Close the session when the user is done.

## Coming back after a dropped network

When the app's link drops, for example when a phone moves from Wi-Fi to mobile
data, the session goes on without it for a while. ElevenLabs agents are the
exception: a dropped link ends the call (see [ElevenLabs agents](#elevenlabs-agents)). The relay keeps the provider
connected and holds the provider's messages for the app, up to 512 messages or
8 MB. The app comes back to the **same** session:

1. Open the WebSocket again with the same ticket and
   `x-agw-relay-messages: 1`. The ticket may have expired by then; it is still
   accepted for coming back.
2. Send `{"type":"agw.reconnect","secret":"…"}` as the first message, within
   10 s.
3. The relay answers `agw.session.resumed`, then sends what it held, then
   everything new. Start the received-byte count from zero on the new link.

If the old link still looks open, the new one takes over anyway, and the relay
closes the old one with `1000 reconnected`. Keep the old link open until
`agw.session.resumed` arrives: closing it first ends the session. Messages the
provider sent to the old link until then still belong to the session.

The app has about 90–120 s after its last message to come back. Messages that
were on their way to the dying link when it dropped can be lost; the provider
usually started its answer again if you ask again.

The Swift `LiveSession` does all of this on its own. Call
`session.reconnect()` when you know the network changed, to move at once
instead of waiting for the old link to fail.

## When to start a new session

Ask the gateway for a new session, naming the old one in `takes_over`, when:

- the app gets `4000 session_ended` or `ticket_expired` while coming back: the
  relay no longer holds the session;
- the session ended with `4000 heartbeat_timeout`, `1000 provider_closed`, or
  `1000 time_cap`;
- the Swift client ends with code `0` and `reconnect_failed`, `link_lost` or
  `send_queue_full`.

iOS suspends an app soon after another app takes the audio or the app goes to
the background without audio. If it stays suspended for more than about
90 s, the relay ends the session, and the app learns it when it runs again.
Start a new session then.

## Close codes

| Code and reason | What happened | What to do |
| --- | --- | --- |
| `1000` with `time_cap`, `client_closed` or `provider_closed` | The session ended normally. | Start a new session if the user goes on. |
| `1000` with `budget_stop` or another limit's code | A limit was reached. | Don't start a new session until the limit allows it again. |
| `1000 replaced` | A newer session of the same user took this one's place. | Nothing; the newer one goes on. |
| `1000 reconnected` | The app came back on a newer link, and this older link was let go. | Nothing; the session goes on there. |
| `4000 heartbeat_timeout` | Nothing came from the app for 90 s. | Start a new session. |
| `4000 client_too_slow` | The app fell about 30 s behind. | Start a new session; send received-byte reports. |
| `4000 session_ended` or `ticket_expired` | The session can't be taken back. | Start a new session with `takes_over`. |
| `4000 session_active` | Another link is already on this session, or the reconnect secret was wrong. | When coming back, try again with the right secret. |
| `4000 adapter_unknown` | The gateway and the relay are on different releases. | Try again later. |
| `4000` with another reason, such as `start_queue_full` | The session never started. | Start a new session. |
| `1008 rate_limited` | More than 2,000 messages in 10 s. | Send fewer, larger messages. |
| `1008` with another reason, such as `setup_required` | The relay or the provider refused a message. | Fix the message. |
| `1009 frame_too_large` | A message over 256 KB. | Send smaller messages. |
| `1011 internal_error` | The relay failed. | Start a new session. |

## Provider notes

- **OpenAI Realtime.** A `session.update` that names another model is sent on
  with the session's model.
- **Gemini Live.** The relay keeps the conversation going across Gemini's own
  connection limits: when Gemini closes a connection, the relay opens a new
  one to the same conversation, and your link stays open. You never get
  `goAway` or `sessionResumptionUpdate`. A `setup` that sets its own
  `sessionResumption` has it removed.
- **Gemini Live refusals.** When Gemini refuses something you sent right after
  the setup, the session ends with Gemini's own close code and reason, such as
  `1007` or `1008`, or `1011` when Gemini's code can't be passed on. Read the
  reason: sending the same setup again gets the same refusal.
- **xAI voice.** xAI's `ping` does not keep a session alive. Send the
  heartbeat.
- **OpenAI GPT-Live.** Send `session.start` first; its model is set to the
  session's. Its backend may use a model your app may call through Responses,
  with function tools only, at the standard `service_tier`; transcript
  `triggers` are not allowed. Anything else ends the session with `1008` and a
  reason such as `backend_model_not_allowed`. A restart of the relay ends a
  GPT-Live session for good: start a new one.
- **ElevenLabs text to speech.** Send ElevenLabs' own messages: the first with
  `text` set to a single space, then your text, then `{"text": ""}` to finish.
  The voice is the one in the path and the model the session's: no message can
  change them. A credential in a message (`xi-api-key`, `xi_api_key`, `authorization`) is
  removed, and a binary message is dropped: ElevenLabs' messages are text.
  ElevenLabs doesn't support `eleven_v3` or `eleven_v4` on this path, and
  ends such a session with its own error. The session is charged by the
  characters of the text you send, as a text-to-speech call is.
- **Deepgram speech to text.** Send the audio as binary messages, and
  Deepgram's own `KeepAlive`, `Finalize` and `CloseStream`. The gateway counts
  the session's time as the longer of two: the audio Deepgram reports it
  heard, and the time from your first audio to the end of the stream.

## OpenAI Realtime over WebRTC

With WebRTC, the audio goes between the device and OpenAI directly, and the
relay only watches the call. Turn on the `openai.realtime.calls` operation for
the app, and ask for a session with `{"path": "v1/realtime/calls", "model": "gpt-realtime-2.1"}`.
The answer's `relay_url` is an `https` address. There is no WebSocket to the
relay:

1. Make the WebRTC offer as for OpenAI, with its `oai-events` data channel.
2. `POST` it to `relay_url` with `Authorization: Bearer <ticket>`, as OpenAI
   takes it at `v1/realtime/calls`: the SDP alone (`Content-Type: application/sdp`),
   or a form with `sdp` and `session`, the session's settings as JSON.
3. Apply the answer, a `201` with OpenAI's SDP, and talk to OpenAI over the
   connection as usual.

The session's model is the one you asked the gateway for, whatever `session`
names. A refused offer gets JSON with a code, such as `400 offer_invalid` for a
form with no `sdp`, `409 session_active` for a second offer with the same
ticket, or `502 provider_unavailable` when OpenAI refused the call.

The relay ends the call at `ends_at`, or when a limit is reached. When the user
is done, close the peer connection: OpenAI then ends the call within seconds.

About once a minute your data channel gets a `session.updated` that changes
nothing: the relay's way to keep watching the call. It can arrive while your
own `session.update` waits for its answer, and its `event_id` is OpenAI's.
So don't match `session.updated` to your updates by count or id: compare each
one with the last `session.updated`, and ignore one that is unchanged. Don't
compare it with `session.created`: OpenAI sends a `session.updated` of its own
right after the start.

## ElevenLabs agents

An ElevenLabs agent call connects the app to one of your ElevenLabs agents,
through the relay.

- **List the agents in the app's settings.** Turn on `elevenlabs.agent` for the
  ElevenLabs connection, and list the agents the app may start, by their ids, in
  the connection's `models`. The agent is the session's model: the app names it
  as `agent_id` in the path's query, or as `model`. Of the query's other
  options, only `branch_id` and `environment` go on.
- **Set up each agent in ElevenLabs first.** In the agent's security settings,
  turn its authentication on, so only the gateway can start a call, and leave the
  override for the conversation's maximum duration off. The gateway reads the
  agent from ElevenLabs when you list it, and refuses an agent set up otherwise.
  It reads it with the connection's key, so the key must be allowed to read
  agents.
- **Send ElevenLabs' own messages**, as its WebSocket API has them. The first
  message may override only the agent's greeting
  (`conversation_config_override.agent.first_message`), and may carry
  `dynamic_variables` and `source_info`. Any other field or override, such as
  the maximum duration, ends the call with `1008 override_not_allowed`. The
  conversation's `user_id` is set by the gateway, and a `user_id` the app sends
  is replaced. It is sent only for an end user the gateway verified (App Attest,
  or your sign-in provider's token), as `<app id>:<hash>`: the app's id, a `:`,
  and the first 32 hex characters of the SHA-256 of the user's id. So the same
  person in two apps that share an agent has two histories. With an app key and
  the end user in a header, or with no end users, no `user_id` is sent.
  Answer ElevenLabs' `ping` with a `pong`, and send the heartbeat: the `ping`
  doesn't keep a session alive.
- **A dropped link ends the call.** Coming back to the same call is not
  possible: ElevenLabs makes every new connection a new conversation. Start a new
  session. Clear the audio left from the old call first, give the new call a
  short greeting with `first_message`, and send the earlier turns as a
  `contextual_update` if the agent should know them.
- **If ElevenLabs refuses the call** (a deleted agent, say), the session never
  starts: `4000 provider_unavailable`.
- **ElevenLabs' own limits apply.** Your ElevenLabs plan allows a number of calls
  at once across its workspace (6 on Starter). Calls above it may run at a
  higher price, wait in a queue, or be refused, depending on the agent's
  settings: see [Voice in an iOS app](#voice-in-an-ios-app). An app may open
  10 voice sessions at once by default.
- A few minutes after a call ends, its charge is corrected to ElevenLabs' own
  figure for the conversation, when the connection's key may read the agent's
  conversations.

### Voice in an iOS app

ElevenLabs' own Swift SDK talks to agents over WebRTC only, so it can't go
through the relay. The Swift package has a voice client of its own for this:
add the `AppAIGatewayElevenLabs` product to your target, beside
`AppAIGateway`. It is a separate library, so apps that don't use it stay
small.

Before the first call:

- add `NSMicrophoneUsageDescription` to the app's `Info.plist`, and ask for
  microphone permission before you start;
- turn on the `audio` background mode, so a call goes on with the screen
  locked or the app in the background.

```swift
import AppAIGateway
import AppAIGatewayElevenLabs
import Foundation

/// The call screen's state: it keeps the voice client for the whole call.
@MainActor
final class CallScreenModel {
    let voice: ElevenLabsVoiceClient
    let variables: [String: ElevenLabsVoiceClient.DynamicVariable] = ["user_name": "Ann"]
    // What the screen shows.
    private(set) var connected = false
    private(set) var queue: String?
    private(set) var lines: [String] = []

    init(gateway: AppAIGatewayClient) {
        voice = ElevenLabsVoiceClient(gateway: gateway, agentID: "agent_7201m7pd…")
    }

    func run() async throws {
        var restarts = 0
        try await voice.start(dynamicVariables: variables)
        call: for await event in voice.events {
            switch event {
            case .connected:
                connected = true
            case .message(let json):
                if let status = queueStatus(json) { queue = status }
            case .userTranscript(let text), .agentResponse(let text):
                lines.append(text)
            case .ended(let ending) where ending.connectionLost && restarts < 2:
                // A new conversation, with a short greeting and the earlier turns.
                connected = false
                queue = nil
                restarts += 1
                try await voice.start(
                    firstMessage: "Sorry, the line dropped.",
                    dynamicVariables: variables,
                    context: ElevenLabsVoiceClient.contextualUpdate(for: voice.transcript)
                )
            case .ended:
                // Ended on purpose (by the app, the agent or a limit), or lost too often.
                connected = false
                break call
            default:
                break
            }
        }
    }

    /// ElevenLabs' `queue_status`: `waiting`, `admitted` or `timed_out`.
    func queueStatus(_ json: String) -> String? {
        let message = (try? JSONSerialization.jsonObject(with: Data(json.utf8))) as? [String: Any]
        guard message?["type"] as? String == "queue_status" else { return nil }
        return (message?["queue_status_event"] as? [String: Any])?["status"] as? String
    }
}
```

`.connected` means ElevenLabs started the conversation and sent its metadata.
The agent may still be busy: when your ElevenLabs workspace is at its limit
on calls at once, ElevenLabs can hold the call in a queue (see below). It then
sends a `queue_status` message, which comes as a `.message`:

- `waiting` comes right after the conversation starts. Show that the call is
  waiting. ElevenLabs plays hold audio meanwhile, which the client plays like
  the agent's speech.
- `admitted` means the agent takes the call now.
- `timed_out` means the wait was too long. ElevenLabs then ends the call.

A call that the agent takes at once gets no `queue_status`.

Keep the client where the call screen keeps its state, as here, not in a
local variable. A client that is let go ends the call and stops its audio at
once, so the end of the loop would cut off the agent's goodbye.

A new greeting with `firstMessage` works only if the agent allows it. In
ElevenLabs, open the agent's **Security** settings and turn on the override
for the **first message**. Without it, ElevenLabs refuses the new
conversation, so the first try to start again after a lost connection fails.

Use one client for one call. Call `voice.end()` to hang up. What the client
does for you:

- **It records and plays the audio.** It uses the iPhone's voice processing,
  so the agent doesn't hear itself on the speaker. It works with the speaker,
  the earpiece and AirPods, and goes on when iOS changes the audio setup, such
  as after another app took the audio for a while.
- **It clears the agent's audio when the user talks over it.** ElevenLabs
  sends a whole answer much faster than it plays, so a long answer can be
  minutes of queued audio. On an interruption that audio is cleared at once.
- **`stopSpeaking()` is a stop button.** ElevenLabs often ignores a short
  spoken "stop" while the agent talks, so give the user a button. It clears
  the answer and tells the agent the user didn't hear the rest.
- **Audio already received plays to its end** when a conversation ends, so a
  goodbye is heard in full. Starting a new conversation clears it first.
- **A lost connection means a new conversation.** The client first tries to
  keep the same one on a new link, such as when the phone moves from Wi-Fi to
  mobile data. When that can't work, the conversation ends with
  `connectionLost` set. `start()` again begins a new conversation that takes
  the old session's place. The new agent knows nothing of the old
  conversation, unless you send it the earlier turns, as above.
- **Answer the agent's tools and send other messages** with `send(text:)`, in
  ElevenLabs' own format. Messages the client doesn't handle itself come as
  `.message` events.

**Other voices near the phone break turn-taking.** ElevenLabs decides when
the user has finished speaking. People talking nearby, or a TV, keep the
user's turn open, and the agent may not answer for a long time. Louder voices
can cut the agent off. The phone's Voice Isolation doesn't help, because it
removes sounds that aren't a voice, not other voices. For noisy places, give
the user push-to-talk or a mute button: set `isMicrophoneMuted`. The client
then sends silence, so ElevenLabs still sees the user's turn end.

**Mind ElevenLabs' limit on calls at once.** Your ElevenLabs plan allows a
number of calls at once, 6 on Starter. The limit is for the whole ElevenLabs
workspace: every agent, and every app that uses the same workspace, shares
it. Above it, what happens depends on the agent's settings in ElevenLabs:

- With burst pricing on, ElevenLabs still serves extra calls, up to its own
  limit for bursts, and charges their minutes at twice its usual rate.
- Without burst pricing, or past the burst limit, ElevenLabs holds the extra
  calls in a queue until a place is free, when call queueing is on (it is by
  default), or refuses them.

An app may open 10 voice sessions at once by default. You can lower
that with `limits.per_app.sessions.conversational` in the app's
[settings](/applications/limits). That caps only this app's share of the
workspace's calls: calls from your other apps and agents still count toward
ElevenLabs' limit.

**If the voice client doesn't suit your app,** use ElevenLabs' official SDK
over WebRTC instead. List ElevenLabs' token path,
`GET v1/convai/conversation/token`, as a
[passthrough](/applications/provider-access#passthrough) path on the
ElevenLabs connection, and have the app get its token through the gateway.
The call itself then runs between the app and ElevenLabs directly: the gateway
checks who asks for the token, but the call's minutes are outside the app's
budgets and usage, and no time cap applies. A token can also start more calls
for about 15 minutes.

## A live provider the gateway doesn't know

A [custom provider](/providers/custom-base-urls#a-websocket-path-for-live-sessions)
can list one WebSocket path for live sessions, with your price per minute:

```json
{"method": "GET", "path": "v1/live", "websocket": true, "per_minute": 0.06}
```

In the console's **Paths** field, or with `agw provider add --path`, write it
as `GET v1/live websocket $0.06/min`.

- The path is a `GET`, with no API style, price per request or field settings.
  A path without a price per minute is refused when you save it. A provider
  lists one such path.
- An app reaches it once it allows
  [passthrough](/applications/provider-access#passthrough) on that provider.
  Start the session as above, with the path and no model, such as
  `{"path": "v1/live?voice=alloy"}`.
- The query goes to the provider as it is, except fields that carry a
  credential (a key, a token, a secret or an authorization, such as `api_key`
  or `apiKey`), which are removed.
- The relay sends your provider key only in the key header the provider's
  settings name, in its format. The device never sees it.
- The relay passes every message both ways as it is, and reads none of them.
  So it cannot remove a credential your app puts inside a message: send none.
- The session is charged by its connection time, from when the relay connects
  to the provider to when the session ends, at your price per minute. The time
  cap, the heartbeat and coming back after a dropped network work as for any
  session.
- It counts toward the limit on open voice conversations, not streams.
- An HTTP request to the path gets `403 path_not_allowed`: the path serves live
  sessions only.
