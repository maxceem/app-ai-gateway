---
title: Errors and limits
description: The error format, the gateway's errors, and how to handle limits and failures.
---

Every refusal from the gateway is JSON with one `error` object:

```json
{
  "error": {
    "code": "app_rate_limited",
    "message": "…",
    "data": { "scope": "user" }
  }
}
```

- `code` does not change between releases. Your app should act on it.
- `message` is for people and logs. It may change.
- `data` is there only for codes that need more, such as which limit was
  reached.

Every `429` the gateway itself sends, and `503 service_unavailable`, carries a
`Retry-After` header with the seconds to wait. A provider's own `429` is passed
on with the provider's headers, and may have none.

A provider's own error is not in this format. It is passed to your app as the
provider sent it, with the provider's status. A provider's error may have an
`error.code` too, so that field alone does not say where an error came from.
Keep the HTTP status, and the provider's request ID when there is one. The
app's **Errors** and **Usage** tabs show what happened.

## Signing in and calling

| Code | Status | Meaning | What to do |
| --- | --- | --- | --- |
| `auth_required` | 401 | No app key or gateway token, or one that is wrong, revoked or expired | Get a new gateway token once, and try again. If it happens again, check the app key |
| `auth_required` | 403 | The user is blocked, or the app key was refused when trading it for a gateway token | Do not retry. See [Blocking](/applications/users#blocking) |
| `assertion_required` | 401 | A request with an iOS app's gateway token has no `X-AppAttest-Proof`, and the app checks App Attest on every request | Sign the request. If the app was switched to every request after the token was issued, get a new token and sign the request again. See [Sign each request](/integrate/ios#4-sign-each-request) |
| `attest_failed` | 403 | An App Attest proof was refused: malformed, made by a key the gateway does not know, made over another request, or used already. The message says which | Build and sign a new request, and send it once. If it happens again, register the key again |
| `issuer_token_rejected` | 403 | The sign-in token did not pass | See [What the app sends](/applications/auth-policy/user-authentication#what-the-app-sends) |
| `issuer_claims_missing` | 403 | The sign-in token passed, but a paid user's claim is not in it yet | See [Subscription check](/applications/auth-policy/subscription-check) |
| `issuer_verification_unavailable` | 503 | The identity provider's keys could not be read | Try again later, waiting longer each time |
| `auth_method_not_supported` | 400, 403 or 404 | The app is not set up for this call, such as App Attest sign-in on a server app, or `/me` on an app with no users | Fix the app's settings or the call |
| `invalid_request` | 400 | The request is malformed: a bad body, a missing `X-App-Version` or end-user header, or a field the operation does not allow | Fix the request. The message says what is wrong |
| `rate_limited` | 429 | Too many sign-in calls from one network address. `data.scope` names the route: `app_auth_challenge`, `app_auth_register`, `app_auth_token` or `app_auth_failure` | Wait `Retry-After` seconds. A real app almost never gets this: look for a retry loop |

`rate_limited` protects the sign-in routes themselves: 60 calls a minute to
each, per app and network address. It is not one of the limits you set on your
app.

## Limits you set

| Code | Status | Meaning | What to do |
| --- | --- | --- | --- |
| `app_rate_limited` | 429 | A request limit on the app refused the call. `data.scope` is `install`, `user` or `app` | Wait `Retry-After` seconds. `install` or `user`: slow this caller down. `app`: the whole app is busy |
| `app_budget_exhausted` | 429 | A monthly budget on the app is spent. `data.scope` is `apple_account`, `install`, `user` or `app` | Wait for next month, or raise the budget |
| `max_output_tokens_exceeded` | 403 | The request asks for more output than the app allows | Ask for less |
| `payload_too_large` | 413 | The body is too large: over 20 MiB on a proxy or preset request, or over 256 KiB on a sign-in call | Send less |

See [Limits and blocking](/how-it-works/limits) for how they are counted.

## What the app allows

| Code | Status | Meaning | What to do |
| --- | --- | --- | --- |
| `path_not_allowed` | 403 | The app does not allow this operation, or the gateway does not know this path for the provider | Use an allowed path, or allow the operation on the app's **Providers** tab |
| `model_not_allowed` | 403 | The model is not in the app's models list | Use an allowed model |
| `pricing_not_configured` | 400 | The model has no price the operation can charge | Use a priced model, or add a price. See [Model pricing](/providers/model-pricing) |
| `preset_not_found` | 404 | The app has no preset with this name | Check the name |
| `job_not_found` | 404 | No job with this ID belongs to this app and user | Use the links the gateway answered with |
| `app_not_found` | 404 | No app has this ID | Check the app ID |
| `app_disabled` | 403 | The app is turned off on its **Settings** tab | Nothing on the device fixes it |
| `not_found` | 404 | Nothing is served at this path or method | Check the URL |

## Providers

| Code | Status | Meaning | What to do |
| --- | --- | --- | --- |
| `provider_not_configured` | 502 | The app does not allow a connection with this slug, or none exists | Allow or add the connection |
| `provider_disabled` | 502 | The connection is turned off | Turn it on |
| `provider_unavailable` | 502 | The connection cannot be used as stored, for example its key could not be opened | Check the connection in the console |
| `provider_error` | 502 | The connection to the provider failed, a job check got no response headers within 30 seconds, or an accepted job submission gave no usable job ID, for example because its body took over 30 seconds | Try again with backoff, unless it was a job submission |
| `provider_error` | 504 | On a proxy or preset request, the provider sent no response headers before the time limit. See [Limits on one request](/integrate/proxy#limits-on-one-request) | Try again with backoff, unless it was a job submission |

## The gateway itself

| Code | Status | Meaning | What to do |
| --- | --- | --- | --- |
| `service_unavailable` | 503 | The platform the gateway runs on failed or was overloaded, or a sign-in or `/me` call took over 10 seconds. Nothing is known to be wrong with the request | Wait `Retry-After` seconds, then try again |
| `internal_error` | 500 | Something failed inside the gateway | Try again with backoff |

## Your account

These concern your gateway account, not your app's users. Nothing on the device
fixes them, so do not ask the user to sign in again.

| Code | Status | Meaning |
| --- | --- | --- |
| `email_unverified` | 403 | The account owner has not verified their email address yet. Open the link in the verification email, or send a new one from the console. Requests are served from then on |

## Handling errors well

- Retry with backoff `provider_error`, `service_unavailable`,
  `internal_error`, and the rate-limit `429`s: `app_rate_limited`,
  `rate_limited` and a provider's own `429`. Wait at least `Retry-After` when
  the answer has it. The exception is a [job](/applications/jobs) submission: never
  resend one on its own after a `5xx`, because the provider may already have
  accepted the job, and charged for it.
- Do not retry `provider_not_configured` or `provider_disabled`: they need a
  change in the console. Do not retry `app_budget_exhausted` either: its
  `Retry-After` runs to the start of next month. An account refusal needs the
  action in its row too.
- Do not send a request again on your own after an answer started, or after
  your app's connection to the gateway was lost. The provider may already have
  done the work, and charged for it.
- On `app_rate_limited` with the scope `install` or `user`, slow that caller
  down. With the scope `app`, show a "busy, try again shortly" state.
- On `issuer_claims_missing`, keep the user signed in, and check again gently.
- Send `X-App-Version` on every request, so the console can tell which release
  a problem belongs to.
- Log `code` and `message`, never the request body, a token or a key.
