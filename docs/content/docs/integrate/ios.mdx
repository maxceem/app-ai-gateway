An iOS app has no key to ship. It proves it is a real install of your app with
Apple's App Attest, trades that proof for a **gateway token** that lasts an
hour, and sends the token with its requests. How this works, and what it
protects against, is explained in
[Identity and entitlement](/how-it-works/identity).

<Callout title="The Swift package">
  The Swift package that does all of this for you is coming with the v2 SDK.
  Until then, this page describes the HTTP calls an app makes, and everything
  on it works today. The earlier Swift package and the demo app work with the
  earlier version of the gateway only.
</Callout>

## Before you start

- An app in the console of kind **iOS app**, with your **Apple Team ID** and
  **Bundle ID**. Its **Sign-in** tab sets which builds are accepted and when
  App Attest is checked. See [Application identity](/applications/auth-policy/identity#ios-apps).
- A real device. App Attest does not run in the simulator.
- If your users sign in, the app's **Who may call** set to
  **Signed-in users only**, and your identity provider's ID token on hand. See
  [User authentication](/applications/auth-policy/user-authentication).

The examples use `https://api.appaigateway.com`. A self-hosted gateway uses its
own API address.

## 1. Get a challenge

```http
POST /v2/apps/{app}/auth/challenge
```

```json
{ "challenge": "q3J0…", "expires_in": 300, "accepts_app_transaction": true }
```

A challenge is base64url text, valid for five minutes, and can be used once.
Get a new one for each step below that needs one.

## 2. Register the install's key

Do this once per install, and again if the gateway no longer knows the key.

1. Create a key with `DCAppAttestService.generateKey()`, and keep its `keyId`.
2. Decode the challenge from base64url, and take the SHA-256 of those bytes.
3. Call `attestKey(keyId, clientDataHash:)` with that hash.
4. Send:

```http
POST /v2/apps/{app}/auth/register
Content-Type: application/json

{ "key_id": "<keyId>", "attestation": "<attestation, base64>", "challenge": "<challenge>" }
```

The answer is `{ "user_id": "…" }`: the install's key ID, or, on an app with
signed-in users, the user's ID. An app with signed-in users also sends
`issuer_token`, the user's ID token. On an app without them, `issuer_token` is
refused.

## 3. Get a gateway token

Get a fresh challenge, then sign this exact text with the install's key, using
`generateAssertion(keyId, clientDataHash:)` and the SHA-256 of the text:

```json
{"app":"<app id>","challenge":"<challenge>","key_id":"<keyId>"}
```

The keys are in this order, with no spaces. Then send:

```http
POST /v2/apps/{app}/auth/token
Content-Type: application/json

{ "key_id": "<keyId>", "assertion": "<assertion, base64>", "challenge": "<challenge>" }
```

```json
{ "access_token": "…", "expires_in": 3600, "verify_on": "every_request" }
```

An app with signed-in users also sends `issuer_token`, as in step 2.

`verify_on` says whether the requests you send with this token must be signed:
`every_request` means yes, `token_exchange` means the token is enough.

### Budgets per Apple Account

An app can count its monthly budget per Apple Account rather than per install.
See [Whose month an iOS budget is](/how-it-works/limits#whose-month-an-ios-budget-is).
For that, when the challenge answered `accepts_app_transaction: true`, also
send StoreKit's `AppTransaction` as its signed JWS text, in `app_transaction`,
and sign it with the rest. Add a fourth key to the signed text, the unpadded
base64url SHA-256 of the JWS:

```json
{"app":"<app id>","challenge":"<challenge>","key_id":"<keyId>","app_transaction":"<hash>"}
```

Without a transaction, or with one the gateway cannot check, such as one from
an Xcode StoreKit setup, the install is counted on its own. It is never
refused for that.

## 4. Sign each request

Send the gateway token, and your app's version, with every request to the
provider proxy, presets and jobs:

```http
Authorization: Bearer <access_token>
X-App-Version: 1.4.2
```

When `verify_on` is `every_request`, also send `X-AppAttest-Proof` with each
request, including `GET /v2/apps/{app}/me`:

```text
X-AppAttest-Proof: v1.<unix seconds>.<nonce>.<assertion>
```

- `<nonce>` is 16 random bytes, base64url without padding.
- `<assertion>` is `generateAssertion` over the SHA-256 of the text below, in
  base64url without padding.

The signed text is these lines joined by a newline, with no newline at the end:

```text
appaigateway-request-v1
<app id>
<HTTP method, in capitals>
<the URL's path and query, exactly as sent>
<base64url SHA-256 of the body; no body hashes as empty>
<base64url SHA-256 of the gateway token>
<unix seconds, as in the header>
<nonce, as in the header>
```

All base64url values here have no padding.

- **Build the whole request first**, body and query included, then sign it,
  and send it unchanged. Other headers may be added after.
- **Keep paths plain ASCII.** The gateway reads the path as a standard URL
  parser does. A path with spaces, quotes or other characters a parser
  rewrites is signed over text the gateway does not see.
- **One proof per request.** Each assertion's counter is accepted once, so a
  retry is a new request with a new proof.
- The device's time is signed, but not compared with the gateway's clock, so a
  wrong clock is not refused.

## 5. Keep the token fresh

The token lasts an hour. Get a new one, with steps 1 and 3, before it ends.

- On `401 auth_required`, get a new token and send the request again, once.
- On `401 assertion_required`, the app was switched to sign every request after
  this token was issued. Get a new token, which now says `every_request`, and
  sign the request.
- On `403 attest_failed`, build and sign the request again, and send it once.
  If it happens again, register a new key with step 2.

Every code is in [Errors and limits](/integrate/errors).

## Report a failure on the device

When a step after the challenge fails on the device, the app can say why, so
the app's **Errors** tab shows it:

```http
POST /v2/apps/{app}/auth/failure
Content-Type: application/json

{
  "challenge": "<challenge>",
  "step": "attest_key",
  "error": { "domain": "com.apple.devicecheck.error", "code": 2 }
}
```

- `step` is `attest_key`, `generate_assertion`, `issuer_token`, `register` or
  `token`.
- `underlying_error`, with the same shape as `error`, is optional.
- `recovered: true` says the app recovered by itself, such as by registering a
  new key.

The challenge must be one this app was given and has not used. The report uses
it up, so one challenge carries one report. The answer says `recorded: true`
or `false`.

## Show the user where they stand

`GET /v2/apps/{app}/me`, signed like any other request, answers the user's
limits, today's requests, the month's spend and whether they are blocked. See
[What a user can see about themselves](/how-it-works/limits#what-a-user-can-see-about-themselves).
