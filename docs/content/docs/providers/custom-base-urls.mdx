---
title: Custom base URLs
description: Send a connection's requests to another host, add a provider the gateway does not know, and list paths to pass through.
---

A connection sends its requests to the provider's own host unless you give it a
**base URL**. This page covers:

- a base URL on a built-in provider, such as a self-hosted server or Azure
  OpenAI;
- a **custom provider**, for a service the gateway does not know;
- **listing paths**, on either kind of connection.

## A base URL on a built-in provider

Set it in **Base URL (optional)** when you add the connection, or later with
the connection's **Host** action. Leave it empty to use the provider's own host.
**Host** is not offered on a connection through Cloudflare AI Gateway, or on a
custom provider. To change a custom provider's base URL, send `baseUrl` with
its key through `PUT /v2/admin/providers/{id}`.

Everything else stays the provider's: the operations, the paths, the header the
key is sent in, and the prices. The path your app sends after the slug is
joined onto the base URL:

```text
Base URL:   https://llm.example.com/
Your app:   POST /v2/apps/my-app/proxy/vllm/v1/chat/completions
Sent to:    https://llm.example.com/v1/chat/completions
```

Do not put `v1/` in both. **Test key** calls the provider's test path at the
base URL too. A server that does not have that path answers `404`, which proves
nothing either way.

```http
POST /v2/admin/providers
Content-Type: application/json

{
  "type": "openai",
  "name": "Self-hosted Llama",
  "slug": "vllm",
  "secret": "…",
  "baseUrl": "https://llm.example.com/"
}
```

A connection goes either to a base URL or through Cloudflare AI Gateway, not
both, so the field is hidden while **Send through Cloudflare AI Gateway** is on.

### What it is for

- **A server you run** that speaks a provider's API, such as vLLM, SGLang or
  llama.cpp's server. Choose OpenAI as the provider.
- **A provider's regional host**, such as xAI's `https://us.api.x.ai/`. Its
  requests are priced at that region's price. See
  [Service modes](/providers/model-pricing#service-modes).
- **Another region of ByteDance Ark**, whose keys work in one region only.
- **A proxy of your own** in front of a provider, as long as it speaks that
  provider's API as it is.
- **Azure OpenAI**, described [below](#azure-openai).

A model your own server runs is not in the price list. Add
[your own price](/providers/model-pricing#your-prices) for it, or requests for
it are refused with `400 pricing_not_configured`. `$0` is a valid price for a
model that costs you nothing per request.

### What the URL must be

The gateway checks a new or changed base URL when you save it. Each refusal says
what is wrong.

| Rule | Refused, for example |
| --- | --- |
| `https` only | `http://…` |
| No user name or password, query string or fragment | `https://user:pass@host/`, `https://host/?x=1` |
| No port other than 443 | `https://host:8443/` |
| A public domain name, never an IP address | `https://127.0.0.1/`, `https://[::1]/` |
| A dot in the name, and none at the end | `https://vllm/`, `https://host./` |
| No local-only ending | `.local`, `.localhost`, `.internal`, `.lan`, `.corp`, `.home`, `.test`, `.example` and similar |
| No empty, `.` or `..` segment, or encoded `/`, in the path | `https://host/a//b/` |
| At most 200 characters | |
| Not Cloudflare AI Gateway's host | Use the connection's own [Cloudflare setting](/providers/gateways). |
| Not another built-in provider's host | `https://api.anthropic.com/` on an OpenAI connection. Add it as that provider, or as a custom provider. |
| On the provider's own host, its plain address only | `https://api.x.ai/v1/` on an xAI connection |

The URL is saved in one form: a lowercase host and one slash at the end. So
`https://LLM.Example.com/v1` is saved as `https://llm.example.com/v1/`.

The gateway never follows a redirect from the provider, so a redirect cannot
send a request, or its key, anywhere else.

### Changing the host

Open the connection's **Host** action. The dialog, **Host**, says where the
connection's requests go.

- **A new base URL** needs the key again: the **API key** field appears, and
  **Save** stays off until you fill it. A stored key is never sent to a new host
  it was not given for.
- **Back to the provider's own host**, by emptying the field, either tick
  **Send the current key to …**, which names the provider's hosts, or type a
  replacement key.

The same through the API. A new `baseUrl` needs `secret` in the same request,
or it is refused with `400 invalid_request`. `null` goes back to the provider's
own host and keeps the key:

```http
PUT /v2/admin/providers/{id}
Content-Type: application/json

{ "baseUrl": "https://eu.llm.example.com/", "secret": "…", "revision": 7 }
```

To find out first whether the key works at the new host, send the same `type`,
`secret` and `baseUrl` to `POST /v2/admin/providers/test`.

<Callout type="warn" title="A base URL receives the key">
  Every request to a connection with a base URL carries its key to that host.
  Only you can set it, from the console or the management API. No app and no
  end user can change it. The gateway refuses addresses that are plainly local,
  but it cannot see where a public name points. So enter only a host you trust.
</Callout>

### Azure OpenAI

Choose OpenAI as the provider, and put `/openai/` in the base URL:

```text
Base URL:   https://YOUR-RESOURCE.openai.azure.com/openai/
Your app:   POST …/proxy/azure/v1/chat/completions
Sent to:    https://YOUR-RESOURCE.openai.azure.com/openai/v1/chat/completions
```

Azure's `v1` API takes the resource key as `Authorization: Bearer`, which is how
the gateway sends an OpenAI key.

- The older Azure API, which needs an `api-version` query and an `api-key`
  header, does not work: a base URL cannot hold a query.
- Microsoft Entra ID tokens do not work. They expire quickly, and a connection
  holds one fixed key.
- The `model` your app sends is your deployment's name. Deployment names are not
  in the price list, so add your own price for each one.

## Custom providers

A custom provider is a service the gateway does not know, at a base URL you
give. It serves only the paths you list.

In **Add provider**, choose **Custom provider** and fill in:

| Field | What to enter |
| --- | --- |
| **Base URL** | Its `https` address, such as `https://llm.example.com/v1/`. The [rules above](#what-the-url-must-be) apply, Cloudflare AI Gateway's host included. The two rules about built-in providers' hosts do not. |
| **Key header** | The header the key is sent in. `authorization` by default. |
| **Key format** | The header's value, with `{key}` where the key goes. `Bearer {key}` by default. |
| **API key** | The service's key. |

The dialog then explains what listed paths give up (see
[Listing paths](#listing-paths)). Tick **I understand, and want to add this
provider**; **Add provider** stays off until you do.

The key header cannot be one that HTTP itself or the gateway uses, such as
`host`, `content-type`, `cookie`, `user-agent`, `x-end-user-id` or
`x-app-version`, or one starting with `cf-`, `x-agw-` or `sec-`. **Test key** sends
nothing for a custom provider, because no call is known to be free there. A
custom provider cannot go through Cloudflare AI Gateway.

Through the API, a custom provider needs `type: "custom"`, `baseUrl` and
`auth`:

```json
{
  "type": "custom",
  "name": "Our model server",
  "slug": "ours",
  "secret": "…",
  "baseUrl": "https://llm.example.com/v1/",
  "auth": { "header": "authorization", "format": "Bearer {key}" },
  "passthrough": [{ "method": "POST", "path": "chat/completions", "style": "openai-chat" }]
}
```

### Paths with an API style

A path you list on a custom provider may name an API style. The gateway then
serves it like a built-in provider's operation of that style: it reads the
model, checks it against the app's models list, measures the usage, and prices
it at your prices for the connection. Add a price for each model, or requests
are refused with `400 pricing_not_configured`.

| Style | API |
| --- | --- |
| `openai-chat` | Chat Completions |
| `openai-completions` | Legacy completions |
| `openai-responses` | Responses |
| `anthropic-messages` | Anthropic Messages |
| `openai-embeddings` | Embeddings |
| `openai-images` | Image generation |
| `openai-transcription` | Speech to text |
| `openai-speech` | Text to speech |

Each style is an operation named `custom.<style>`, such as `custom.openai-chat`,
which an app allows on its **Providers** tab. List one path per style; each is a
`POST`. A path with no style is passed through, as on a built-in provider.

## Listing paths

On a built-in provider, **Passthrough paths** lists paths the gateway has no
operation for, such as OpenAI's `v1/files`. On a custom provider, **Paths**
lists every path it serves. The app reaches them as described under
[Passthrough](/applications/provider-access#passthrough).

Write one path per line: the method, the path, then a price or, on a custom
provider, an API style:

```text
GET v1/files/{file_id} $0.001
POST v1/files
POST chat/completions openai-chat
```

- The method is `GET`, `POST`, `PUT`, `PATCH` or `DELETE`.
- `{name}` stands for one segment, such as an ID, and two never stand next to
  each other. It comes after any API prefix the gateway knows, such as `v1` or
  DeepSeek's `beta`, and at least one fixed segment, the endpoint's name. So OpenAI's
  `v1/files/{file_id}` can be listed, and so can `predictions/{id}` on a custom
  provider whose base URL ends in `/v1/`. `v1/{id}` cannot.
- A price, such as `$0.002`, is charged for each answer the provider accepts.
  Without one, the path is not priced, and budgets do not limit it.
- A path that could match requests of one of the provider's operations, or of
  another API-style path, is refused: it would take them without counting them.
  Allow that operation on the app instead.
- The same pattern listed twice is refused. Otherwise plain paths may overlap,
  and the more specific one wins: `GET v1/files/search` serves that request,
  at its own price, ahead of `GET v1/files/{file_id}`.
- A connection lists up to 100 paths.

The first time you list paths on a built-in provider, the dialog shows what
passing paths through gives up, and asks you to tick **I understand, and want
these paths passed through**. **Save paths** stays off until you do:

- a path without a price is not priced, so budgets do not limit it, though
  request limits still apply;
- IDs the provider returns, such as file IDs, are not tied to the app, so
  another app with the same provider key could read them. Give such paths a
  connection, and a provider key, of their own.

For some paths the provider knows, such as the token paths for live sessions,
the gateway suggests **safe defaults**: request fields it sets over what the app
sends, such as a 60-second expiry. They are set when you save, and you can
change or remove each one. Through the API they are `set_fields` on the path.
