---
title: Limits and blocking
description: How the limits you set on your app's users are counted, and how blocking differs from a limit.
---

An app can limit each of its callers and the whole app: requests per minute,
requests per day, and a monthly budget in dollars. This page explains how those
limits are counted. The fields themselves, and how to set them, are on
[Limits](/applications/limits).

## Who a caller is

On a server app, each caller is one user. On an iOS app, request limits count
each **install**: one copy of your app on one device. Reinstalling the app
starts a new install, and one person on a phone and a tablet is two. So each
device a person uses has its own minute and its own day.

## Whose month an iOS budget is

An iOS app chooses whose month its per-caller budget counts:

| Budget counted per | What it counts together |
| --- | --- |
| **Each Apple Account** (`apple_account`), the default | Every install of one Apple Account: on all of that person's devices, and across reinstalls |
| **Each install** (`install`) | One install alone. Reinstalling the app starts a fresh budget |
| **Each signed-in user** (`user`) | Every install of one signed-in user. Only an app with **Signed-in users only** can choose it |

**Each Apple Account** needs nothing from you or your users: no setting, no
prompt and no sign-in. The app sends its App Store transaction, which Apple
signs, when it gets a gateway token. The gateway checks Apple's signature and
your bundle ID, and counts the install against the Apple Account the
transaction names.

An install whose app sent no transaction the gateway could check is counted on
its own, exactly as under **Each install**, and is never refused for it. That
covers builds that use an Xcode StoreKit configuration, and devices where
StoreKit did not answer in time. So a person who keeps a device from reaching
the App Store can still start a fresh budget by reinstalling.

Each member of a Family Sharing group has their own Apple Account, and so their
own budget. TestFlight and development builds use Apple's sandbox, and are
counted apart from App Store builds, even for the same person.

A server app always counts its budget per user.

## Refusals

A request over a request limit is refused with `429 app_rate_limited`. A request
over a budget is refused with `429 app_budget_exhausted`. Both say whose limit
it was in `data.scope`:

- `install`: an iOS app's request limits, or a budget counted per install;
- `apple_account`: a budget counted per Apple Account;
- `user`: a server app's limits, or a budget counted per signed-in user;
- `app`: the whole app's limits.

Both carry a `Retry-After` header with the seconds to wait. For a request limit
it is the time until the window starts again. For a budget it is the time until
the month ends, because a budget only resets then.

Each caller's limits are checked before the whole app's, so one heavy caller
cannot use up the whole app's limit before their own limit stops them.

## How they are counted

- **Request windows are fixed, not sliding.** A user can use a full minute's
  allowance at the end of one minute and again at the start of the next, so a
  burst of up to twice the per-minute value is possible across the change of
  minute. Days change at midnight UTC.
- **Budgets are checked against spend already recorded.** A call's cost is known
  only when its answer is complete. In normal operation the limit reads the
  month's spend again every ten seconds. So a budget can be overrun:
  - by a burst of calls inside those seconds;
  - by one very expensive call;
  - when recording usage is slow;
  - when the check runs out of time, and the call is served rather than refused.
- **Budgets use UTC calendar months.** Turning on a budget part-way through a
  month counts what the month has already spent. Every call adds to its
  install's, its user's and, when known, its Apple Account's month alike. So
  changing whose month an iOS budget counts, mid-month, counts the month so far
  too.
- **A budget of zero refuses every request it covers**, whenever the month's
  spend can be read: the limit compares the spend with the budget before the
  provider is called, so it refuses even a request that would cost nothing. An
  unpriced passthrough call is not covered by budgets. Leave the field empty for
  no limit instead. A request limit
  of zero is refused when you save, as a likely typo.
- **Changes reach every request within a minute** in normal operation. See
  [When changes take effect](/how-it-works/apps-and-providers#when-changes-take-effect).

Per-caller limits need an app that names its users. An app with **No end users**
has nobody to apply them to, so it can set only the whole app's limits. An iOS
app always names its installs.

## Blocking is not a limit

A limit resets; a block stays until you lift it. Blocking a user refuses their
provider calls and their sign-ins, on every install. See
[Blocking](/applications/users#blocking).

## What a user can see about themselves

An app that names its users can call `GET /v2/apps/{app}/me`, signed in the same
way as its other requests. It answers even for a blocked user, and says whether
they are blocked. It also answers the limits that apply and the month's spend.
Where the app sets any per-user limit it answers today's requests too, and what
is left of the daily limit if there is one. Without a per-user limit, requests
are not counted, so today's count is `null`.

On an iOS app the request counts are the install's, and `install_id` names it.
`budget_scope` says whose month the spend is: `apple_account`, `install` or
`user`. It is `install` for an install that sent no transaction the gateway
could check, even when the app counts per Apple Account.

It is meant for showing a user where they stand before they reach a limit. See
[Errors and limits from the client side](/integrate/errors).
