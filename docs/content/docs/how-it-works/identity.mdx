title: Identity and entitlement
description: The three questions the gateway asks about a request, and which combinations an app can be set up for.
---

Every request answers up to three questions. Each app's **Sign-in** tab is
organised around them.

| Question | Answered by | Set under |
| --- | --- | --- |
| Is this my app? | Apple App Attest, or an app key | The app's kind, and for an iOS app its Team ID and Bundle ID |
| Which user is it acting for? | A sign-in token, the app install itself, or a header from your server | **Who may call** |
| Has that user paid? | A claim in the sign-in token | **Paid users only** |

The first question always has an answer. The second and third are optional,
and the third needs the second.

## Is this my app?

An **iOS app** proves itself with Apple App Attest. The device holds a key in
the Secure Enclave. Apple confirms that the key belongs to a genuine install of
your app, and the gateway checks that against your Team ID and Bundle ID. The
app then trades an App Attest assertion for a gateway token that lasts one
hour. By default it also signs every request with the same key. There is no
shared key to build into the app. The Swift package that does all this for an
iOS app is coming with the v2 SDK. Until then, [iOS apps](/integrate/ios)
describes the HTTP calls.

A **server** app proves itself with an app key, a long-lived `agw_…` secret.
With no signed-in users it sends that key with every call. With signed-in users
it trades the key and the user's sign-in token for a gateway token. The key
belongs in a secret manager, never in a client.

## Which user is it?

Knowing the user is what makes per-user limits, per-user usage and blocking
possible. An iOS app's users are either people who sign in with your identity
provider, or each install of the app. A server app's users are people who sign
in, users your server names in a header, or nobody at all. Each choice, and what
it needs, is on [User authentication](/applications/auth-policy/user-authentication).

A user named by a sign-in token is the strongest choice: the gateway checks the
token's signature, issuer and audience before it trusts the user ID inside. An
install as the user works with no sign-in, but a person can get around a block
or a per-install budget by reinstalling the app. A user your server names is
taken on trust, so it belongs only on a server you control.

## Has the user paid?

With signed-in users, the gateway can also require that the sign-in token
carries claims saying the user has paid. The gateway never talks to the App
Store itself. Something else, such as RevenueCat or your own server, writes the
entitlement into the user's token, and the gateway checks for it each time a
gateway token is issued.

Because the claim is written after the purchase, there is a short time when a
paying user holds a token without it. The gateway reports that with its own
error code, `issuer_claims_missing`, so your app can wait instead of asking the
user to sign in again. See [Subscription check](/applications/auth-policy/subscription-check).

## What the gateway token is

An iOS app, or a server app with signed-in users, does not send its user's
sign-in token with every request. It trades its proof and that token once, at
`/v2/apps/{app}/auth/token`, for a **gateway token** that lasts one hour and
stands for both.

Provider proxy and preset requests with a gateway token also carry an
`X-App-Version` header: the app's own version, such as `1.4.2` or `1.4.2 (45)`.
Such a request without it is refused with `400 invalid_request`; `/me` does not
need it. The gateway records it on every charge, so the app's **Usage** tab can
show whether a problem belongs to one release. Only a value shaped like a version
is saved.

A server app with no signed-in users skips the trade and sends its app key
directly.

### When App Attest is checked

Each iOS app has a **Check App Attest on** setting, `verify_on` in its settings,
with two values.

| Value | What the gateway checks |
| --- | --- |
| **Every request** (`every_request`, the default) | The assertion when a gateway token is issued, and a fresh assertion on every request |
| **Token exchange** (`token_exchange`) | The assertion when a gateway token is issued, only; requests carry the gateway token alone |

Either way the gateway token names the install it was issued to, and its Apple
Account when the app sent its App Store transaction. So limits, budgets and
usage are counted the same way in both modes.

### Every request

With **Every request**, an iOS app's gateway token is tied to the App Attest key
of the install it was issued to, and is not enough on its own. Every request
sent with it also carries an `X-AppAttest-Proof` header: an App Attest assertion
that the key signed over that one request. The proof covers:

- your app's ID, the HTTP method, and the request's path and query;
- a hash of the request body;
- a hash of the gateway token itself;
- the device's time and a random value.

The gateway checks the signature against the install's key. Each assertion
carries a counter, and each counter is accepted once, within a window of the
install's 64 most recent ones. So a proof copied off the network cannot be used
again. The device's time is part of what is signed, but the gateway does not
compare it with its own clock: a device whose clock is wrong is not refused.

Someone who copies a gateway token off the network can do nothing with it.
Without the device's key they cannot sign a new request, and a proof copied
with it covers only a request that was already served. A request without a
proof is refused with `401 assertion_required`.

### Token exchange

With **Token exchange**, the assertion is checked once for each hourly token,
and requests carry only the token. A token copied off the network works from
anywhere until it ends, at most an hour later.

## Combinations

| App kind | Who may call | Paid users only |
| --- | --- | --- |
| iOS | Signed-in users only | Available |
| iOS | Anyone with the app | Not available: there is no sign-in token to check |
| Server | Signed-in users only | Available |
| Server | Your server sends the user id | Not available |
| Server | No end users | Not available |

Two pairings do not exist. An iOS app cannot name its own user in a header,
because the device is the one being limited. A server app cannot use the app
install as its user, because it has no attested key.
