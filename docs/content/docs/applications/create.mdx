---
title: Create an application
description: Walk through creating an iOS app or a server app, and what it creates.
---

Open **Apps** and click **New app**. The **Create an app** form asks one thing at
a time, and only what the kind of app you pick needs. You can change every
answer later on the app's **Sign-in** tab, except the app's kind and its ID.

## 1. Name and kind

- **Name**: how the app is listed. The gateway builds the app's permanent ID
  from it: `Calorie Tracker` becomes something like `calorie-tracker-k3f9x1`.
  See [Apps and providers](/how-it-works/apps-and-providers#the-app-id-is-permanent).
- **Where do calls come from?**
  - **iOS app**: calls come straight from the app. Apple's App Attest proves
    each call comes from your real app.
  - **Server**: calls come from your own server, with an app key it keeps
    secret.

## 2. How the app proves itself (iOS only)

Only builds signed with your team and bundle ID can call through this app.

- **Apple Team ID**: ten letters and digits, in your Apple developer account
  under Membership details.
- **Bundle ID**: such as `com.example.app`, from your target's Signing &
  Capabilities in Xcode.
- **Accepted builds**: **Production** covers App Store and TestFlight builds,
  and is the only one on by default. **Development** covers builds run from
  Xcode. Turn it on for a development bundle ID rather than the one you ship.
  See [Application identity](/applications/auth-policy/identity).

## 3. Who may call

Whether calls belong to a user, and how the gateway knows who that is.

For an iOS app:

- **Signed-in users only**: users sign in through your identity provider, and
  the gateway checks their sign-in token.
- **Anyone with the app**: no sign-in. Each install counts as one user.

For a server:

- **Signed-in users only**: your server forwards each user's sign-in token, and
  the gateway checks it.
- **Your server sends the user id**: in the `x-end-user-id` header, unless you
  name another in **Header name**.
- **No end users**: calls are not linked to any user, and limits apply to the
  app as a whole.

## 4. Identity provider (signed-in users only)

Pick where your users sign in. The choice fills in the checking settings from
one or two values you already have.

| Identity provider | You enter |
| --- | --- |
| **Firebase Authentication** | Firebase project id |
| **Supabase Auth** | Project ref |
| **Auth0** | Your Auth0 domain, and the API identifier |
| **Clerk** | Frontend API host, Audience |
| **Custom issuer** | JWKS URL, Issuer (iss), Audience (aud) |

See [User authentication](/applications/auth-policy/user-authentication).

## 5. Paid users only (signed-in users only)

Whether a user must have paid before they can call through this app.

- **Any signed-in user**: signing in is enough. Payment is not checked.
- **Paid users only**: the sign-in token must carry the claims you list. **Add
  RevenueCat entitlement** adds the claim RevenueCat's Firebase function kit
  writes; enter the entitlement's identifier, such as `pro`.

See [Subscription check](/applications/auth-policy/subscription-check).

## What is created

Click **Create app**. The new app is on, and has:

- no providers yet: it may call nothing until you allow a connection on its
  **Providers** tab;
- no limits, no model rewrites and no presets.

A server app also gets its first app key, shown once in a dialog titled **Copy
your app key now**. Copy it before you close the dialog: the gateway keeps only
a hash of it. You can make more keys later on the app's **Keys** tab.

Then you land on the app's **Overview** tab. Its **Ready to serve** section
says what is still missing, and **First requests** has example requests once a
provider is allowed. See [Provider access](/applications/provider-access).

## Through the API

`POST /v2/admin/apps` creates the same thing. The body has `name`, `config` and
an optional `status`, never an `id`. The answer has the app, with the ID the
gateway gave it in `app.id`, and for a server app its first key in
`api_key.key`.

A server app with no end users, allowed to call OpenAI's Responses API through
the `openai` connection:

```json
{
  "name": "Search service",
  "config": {
    "authentication": { "type": "api_key", "end_user": { "source": "none" } },
    "routing": { "providers": { "openai": { "operations": ["openai.responses"] } } }
  }
}
```

An iOS app with users who sign in with Firebase:

```json
{
  "name": "Calorie Tracker",
  "config": {
    "authentication": {
      "type": "apple_app_attest",
      "app_attest": { "team_id": "ABCDE12345", "bundle_id": "com.example.calorietracker" },
      "end_user": {
        "source": "issuer",
        "issuer": {
          "jwks_url": "https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com",
          "issuer": "https://securetoken.google.com/my-app-1a2b3",
          "audience": "my-app-1a2b3",
          "user_id_claim": "sub",
          "required_claims": [],
          "max_token_lifetime_seconds": 86400,
          "provider": "firebase"
        }
      }
    }
  }
}
```

Every setting is described in the
[app settings reference](/automation/agent-manual#application-configuration-reference).
