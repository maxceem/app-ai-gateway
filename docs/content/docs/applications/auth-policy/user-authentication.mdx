---
title: User authentication
description: Tie calls to users who sign in with Firebase, Supabase, Auth0, Clerk or your own issuer, or count each install as a user.
---

**Who may call**, on the app's **Sign-in** tab, decides whether calls belong to a
user and how the gateway knows who that is. Knowing the user is what makes
per-user limits, per-user usage and blocking possible.

## The choices

| Choice | App kind | User ID |
| --- | --- | --- |
| **Signed-in users only** | iOS and server | A claim from a checked sign-in token, `sub` by default |
| **Anyone with the app** | iOS | The App Attest key of the install |
| **Your server sends the user id** | Server | The value of a header your server sends |
| **No end users** | Server | None |

## Signed-in users only

Your app sends a signed JWT from its identity provider. The gateway checks the
signature against the provider's public keys, checks the issuer and audience
against your settings, and takes the user ID from the token.

Pick your provider under **Identity provider**. The choice fills in the checking
settings from the values you enter.

| Identity provider | You enter | What it sets |
| --- | --- | --- |
| **Firebase Authentication** | Firebase project id (from Project settings, not the project number) | Google's shared key set, issuer `https://securetoken.google.com/<project-id>`, audience `<project-id>` |
| **Supabase Auth** | Project ref (the subdomain of your project URL) | Your project's key set, issuer `https://<ref>.supabase.co/auth/v1`, audience `authenticated` |
| **Auth0** | Your Auth0 domain, and the API identifier | Your domain's key set, issuer `https://<domain>/`, audience the API identifier |
| **Clerk** | Frontend API host, Audience | Your Frontend API's key set, issuer `https://<host>`, audience what your JWT template sets |
| **Custom issuer** | JWKS URL, Issuer (iss), Audience (aud) | Exactly what you enter |

Things each provider needs you to know:

- **Firebase** signs every project's tokens with one shared key set, so the key
  set alone names nobody. The issuer and audience are what limit the app to your
  project. Without them a token from any Firebase project would pass, which is
  why both are required.
- **Supabase** must use asymmetric JWT signing keys. A project on the older
  HS256 signing publishes no public keys, so every token is refused.
- **Auth0** puts a slash at the end of `iss`. The setting keeps it; do not
  remove it. With the API identifier as audience, send a JWT access token
  requested for that API, not an ID token whose audience is your client ID.
- **Clerk**'s default session token has no `aud`. Add one in your JWT template,
  because the gateway requires it.
- **Sign in with Apple** works as a custom issuer: issuer
  `https://appleid.apple.com`, audience your bundle ID, JWKS URL
  `https://appleid.apple.com/auth/keys`.

Issuer and audience each take one value or a list. So when you move from one
project or bundle ID to another, you can accept both for a while, then remove the
old one.

### What the app sends

The app sends the identity provider's token in the `issuer_token` field of a
JSON body, with what proves the app itself:

- **A server app** sends its app key in `api_key`, to
  `POST /v2/apps/{app}/auth/token`.
- **An iOS app** takes three steps:
  1. It asks `POST /v2/apps/{app}/auth/challenge` for a challenge.
  2. To register its App Attest key, it sends `key_id`, `attestation` and the
     challenge to `POST /v2/apps/{app}/auth/register`, which answers the
     `user_id`.
  3. To get a gateway token, then and on every later sign-in, it sends `key_id`,
     an `assertion` and a fresh challenge to `POST /v2/apps/{app}/auth/token`.

`/auth/token` answers the gateway token as `access_token`, and the app sends it
with its calls.

The trade can be refused for a bad app key, a blocked user or a malformed body,
like any sign-in. Three codes are about checking the sign-in token itself, and
each says what the app should do next:

| Code | Meaning | The app should |
| --- | --- | --- |
| `403 issuer_token_rejected` | The token did not pass: bad signature, expired, wrong issuer or audience, or no user ID claim | Get a fresh token from the identity provider, try once more, then stop |
| `403 issuer_claims_missing` | The token passed, but a claim required for paid users is not there yet | Get a fresh token from the identity provider, forcing a refresh, and try again. Do not sign the user in again |
| `503 issuer_verification_unavailable` | The gateway could not fetch or read the provider's key set, so the token was never judged | Try again later, waiting longer each time |

Each of these is listed on the app's **Errors** tab. See
[Auth events](/applications/auth-events).

### In the settings

```json
"end_user": {
  "source": "issuer",
  "issuer": {
    "jwks_url": "https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com",
    "issuer": "https://securetoken.google.com/my-app-1a2b3",
    "audience": "my-app-1a2b3",
    "user_id_claim": "sub",
    "required_claims": [],
    "max_token_lifetime_seconds": 86400,
    "provider": "firebase"
  }
}
```

- `jwks_url` must use HTTPS.
- `user_id_claim` names the claim used as the user ID. The console starts it at
  `sub`; through the API it is required.
- `max_token_lifetime_seconds` refuses a token whose own lifetime, its expiry
  minus its issue time, is longer than this. So a provider set up by mistake to
  issue week-long tokens cannot widen the window.
- `token_header`, if set, names one more header that may carry the gateway
  token. Most apps do not need it; see below.
- `provider` only helps the console reopen the same choice; the gateway does
  not use it.
- `required_claims` is the paid-user check. See
  [Subscription check](/applications/auth-policy/subscription-check).

On calls to the provider proxy, the gateway takes the gateway token from the
first of these headers that has a value:

1. `Authorization`;
2. the connection's own key header, such as Anthropic's `x-api-key`;
3. `token_header`, if set.

A preset uses its first connection's key header in step 2. `/me` has no
connection, so it skips step 2.

The gateway does not try the next header if the first holds something else, so
`token_header` works only when the headers before it are empty. With a provider
SDK, it is usually simpler to give the SDK the gateway token as its key: the SDK
then sends it in a header the gateway reads. The gateway removes these headers
before the call reaches the provider.

## Anyone with the app

For an iOS app with no sign-in. The App Attest key names the install, so
per-install limits, blocks and usage all work with nothing the app reports
about itself.

The key lives in the Secure Enclave, for one install of one app on one device.
It does not survive reinstalling the app, or moving to a new phone. So a user
can get around the limits and blocks on an install by starting over. And there is no
sign-in token to look at, so the paid-user check is not available.

```json
"end_user": { "source": "app_install" }
```

## Your server sends the user id

For a server that serves real users and knows who they are. Your server names
the user in a header on every call, and the gateway takes the value on trust.

**Header name** is `x-end-user-id` unless you name another. Its case does not
matter, and it is removed before the call reaches the provider. A value is 1 to
128 printable ASCII characters, without spaces.

The header is required once set. A call without it is refused with
`400 invalid_request`, because an app that allowed it to be missing would count
part of its traffic as nobody's.

This belongs only on a server you control. A client your users run could send
any ID it likes and get around per-user limits. These users cannot be blocked
on the gateway; block them in your server.

```json
"end_user": { "source": "header", "header": "x-end-user-id" }
```

## No end users

For a server with no users to speak of, such as a batch job. Calls record no
user, per-user limits cannot be set, and `GET /v2/apps/{app}/me` answers `404`.
Use the whole app's limits instead.

`end_user` is required on a server app, so an app with no users says so with
`none`.

```json
"end_user": { "source": "none" }
```
