---
title: Application identity
description: How an app proves it is your app, with App Attest for iOS or app keys for a server.
---

The first question about every request is whether it comes from your app. An
iOS app answers with Apple App Attest, set on the app's **Sign-in** tab. A
server app answers with an app key, made on the app's **Keys** tab.

## iOS apps

Only builds signed with your team and bundle ID can call through this app.

- **Apple Team ID**: ten letters and digits, in your Apple developer account
  under Membership details.
- **Bundle ID**: such as `com.example.app`, on your target's Signing &
  Capabilities tab in Xcode.

Apple ties an App Attest key to one install of one app on one device, and the
attestation carries a hash of your team ID and bundle ID. The gateway checks
that hash, keeps the key's public half, and from then on accepts assertions
signed by that key: one each time a gateway token is issued and, unless the app
checks App Attest only then, one on every request. The key never leaves the
Secure Enclave.

Keys are per install. A user who uses your app on a phone and a tablet holds
two keys, and a user who reinstalls the app gets a new one. A new key never
replaces another. Each install has its own request limits; the monthly budget
is, by default, counted across all installs of one Apple Account. See
[Limits](/applications/limits).

### Accepted builds

Apple runs App Attest in two environments, and marks which one in every
attestation. An app accepts one or both, and at least one must stay on.

- **Production**: App Store and TestFlight builds. On by default.
- **Development**: builds run from Xcode. Off unless you turn it on.

A development-signed build can be debugged, and runs on any device with your
team's provisioning profile. That is why Development is off by default. Turn it
on for a development bundle ID, never the one you ship.

Turning an environment off also stops the keys it already let in: on their next
request when the app checks every request, otherwise the next time they get a
gateway token, within the hour. They are refused with `403 attest_failed`, and
the app registers a new key in an environment it still accepts.

Two things no setting changes. App Attest does not work in the Simulator,
because it needs the Secure Enclave. And a development build can attest in
production instead, if you set the
`com.apple.developer.devicecheck.appattest-environment` entitlement to
`production`. That is the better answer when a development build only needs to
reach an app that accepts production builds.

### Check App Attest on

When the gateway checks the install's App Attest assertion.

- **Every request**: each request carries a fresh assertion, so a gateway token
  copied off the network is useless without the device. The default.
- **Token exchange**: the assertion is checked once for each hourly token, and
  requests carry only the token.

With **Every request**, a request without a proof is refused with
`401 assertion_required`. Neither setting changes how limits, budgets and usage
are counted. See [When App Attest is checked](/how-it-works/identity#when-app-attest-is-checked).

### In the settings

```json
"authentication": {
  "type": "apple_app_attest",
  "app_attest": {
    "team_id": "ABCDE12345",
    "bundle_id": "com.example.app.dev",
    "environments": ["production", "development"],
    "verify_on": "every_request"
  },
  "end_user": { "source": "app_install" }
}
```

`environments` may be left out, which means `["production"]`. `verify_on` is
`every_request` or `token_exchange`, and may be left out, which means
`every_request`. `end_user` is required, and is covered under
[User authentication](/applications/auth-policy/user-authentication).

## Server apps

A server app proves itself with one of its app keys. The **Keys** tab lists each
key with its **Name**, the start of the **Key**, when it was **Created**, when it
was **Last used**, and its **Status**.

**New key** asks for a name, so you can tell keys apart, then shows the key once
in a dialog titled **Copy your app key now**. The gateway keeps only a hash, so
there is no way to see the key again. Keep it in your server's secret manager.

**Revoke key** stops a key within a minute. Make the new key first, move your
server to it, then revoke the old one, and the change costs no downtime.

Once revoked, the key is refused with `401 auth_required` or
`403 auth_required`. Gateway tokens made with it stop working too.

### How the key is sent

With no signed-in users, your server sends the key with every call:

```http
Authorization: Bearer agw_…
```

With signed-in users, your server trades the key and the user's sign-in token
for a gateway token instead. See [Server applications](/integrate/server).

### In the settings

```json
"authentication": { "type": "api_key", "end_user": { "source": "none" } }
```

`end_user` is required here too. `none` means the app has no end users; the
other choices are covered under
[User authentication](/applications/auth-policy/user-authentication).

Keys are not part of the settings. `POST /v2/admin/apps/{app}/keys` makes one
and answers its `key` once. `POST /v2/admin/apps/{app}/keys/{key}/revoke`
revokes it.
