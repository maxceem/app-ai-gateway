---
title: Model rewrites
description: Point a model name an app sends at the model the provider should receive.
---

An app's **Rewrites** tab maps a model name the app sends to the model the
provider receives. The app's **Models** list is checked against the name the
app sends, so the target need not be in it. The price, and the usage record, are
the target's.

A rewrite is how you move an app to a newer model without an app release: the
app keeps asking for `gpt-5.4-mini`, and you point that name at a newer model.
For a bigger change, such as another provider or fixed settings, use a
[preset](/applications/custom-endpoints).

To add one, click **Add rewrite**. In the first box, enter the name the app asks
for. It can be a name of your own, such as `my-model`, that no provider has. In
the second, enter the model to send. Click **Save rewrites** to save. The model
sent must have a price, or be served by a provider that reports each request's
cost itself, or saving is refused.

A rewrite applies on every connection, to the model a call through the provider
proxy selects: in the body or a form field, in the query, in the path (as on
Gemini and `fal.run`), or the provider's default when the request names none
(as on Deepgram). It does not
apply to:

- operations whose model is fixed;
- jobs, such as `fal.queue`, which run the model they name;
- presets, which name their models themselves.

It is one step only: its target is never rewritten again.

## In the settings

```json
"routing": {
  "model_rewrites": { "gpt-5.4-mini": "gpt-5.4-nano" }
}
```

`model_rewrites` maps the model name an app sends to the one the provider
receives. The first is the name the app asks for, which may be a name of your
own. The second is the provider's own model name. Leave it out for no rewrites.
